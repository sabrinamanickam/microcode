Curve25519 Field Arithmetic in Goldmont Microcode

A complete technical rundown — from file structure to the last triad — of the two field operations that dominate X25519 (fe_mul and fe_sq over GF(2²⁵⁵−19)) encoded directly in Intel Goldmont microcode patch RAM, and benchmarked against fiat-crypto, the formally-verified C baseline that CryptOpt itself targets.

0.74×
fe_sq microcode / fiat-crypto -O3

The squaring patch runs in ~37 cyc/op versus fiat-crypto's baseline — a ~26% win — in 42 triads. The multiply patch runs in ~58 cyc/op, a ~3% win, in 66 triads. Both fit comfortably inside the 128-triad patch-RAM cap and are validated against an independent schoolbook reference on the published basepoint, 10 000 random vectors, and a 1 000-deep iterated chain.

This document explains the two production patches in simple/asm_op_curve25519.c (squaring) and simple/asm_op_curve25519_mul.c (multiplication). Unlike the Keccak project, these are hand-written triad arrays — there is no generator. The single technique that makes them fast is the MAC accumulator: a 64×64→128 multiply whose high half, low half, and carry bit all flow into different registers inside the same triad, so a five-term multiply-accumulate sum costs almost nothing beyond its five MULs.

The narrative has three threads, woven together below:

  1. Why the patch is shaped the way it is — the radix-2⁵¹ field, the MAC pattern, and the hardware facts that forced each choice.
  2. A line-by-line read of both patches in execution order, with the actual triads.
  3. How the win was built — the packing deltas (88→73→66 for multiply, 43→42 for squaring), the verification methodology, and the honest ceiling.

1. Background

1.1 What microcode patching is on this CPU

On this Goldmont CPU (Intel Atom family, Celeron N3350), microcode is patchable. Each x86 instruction is internally cracked into micro-ops (uops); some instructions execute a sequence of uops fetched from a small on-die patch RAM. The lib-micro infrastructure exposes two primitives:

  • patch_ucode(addr, patch, n) — write our own uops into patch RAM at U7c00…
  • hook_match_and_patch(slot, opcode, addr) — redirect an x86 instruction so executing it jumps into our uops.

Microcode is organized as triads: a unit of 3 micro-ops + 1 sequence word (the seqword controls flow — NOP_SEQWORD falls through, END_SEQWORD returns to the x86 stream). One triad occupies 4 address units, hence the ×4 in address arithmetic. The usable region U7c00–U7dfc holds 128 triads — the hard size cap. fe_mul uses 66 of them; fe_sq uses 42.

1.2 The vmwrite / vmread hooks — the C↔microcode bridge

We hijack instructions that are meaningless in ordinary user code. The standalone test harnesses each hook vmwrite (opcode 0x0cd8) and fire it with vmwrite rcx, rdx. In the integrated X25519 build (full_curve25519.c), the two patches must coexist, so multiply is on the vmwrite hook and squaring is moved to the vmread opcode (0f 78 ca) — two hooks, two patch regions, one binary. The bridge in C pins operands to specific registers, fires the hooked instruction, and declares every clobbered GPR:

register uint64_t *_in  asm("rcx") = (uint64_t *)a;
register uint64_t *_out asm("r15") = out;
asm volatile(
    "push r15\n\t"                // save out-ptr before we destroy r15
    "mov rdi, [rcx]\n\t" …          // load 5 limbs through the rcx pointer
    "lea r15, [rdi + rdi]\n\t" …    // precompute 2·a / 19·a in arch regs (sq only)
    "xor eax, eax\n\t  xor r8d, r8d\n\t" // clear the two accumulators
    "vmwrite rcx, rdx\n\t"          // ← microcode fires here, NO memory access
    "pop rcx\n\t  mov [rcx], rdi\n\t" … // store 5 result limbs
    : "+r"(_in), "+r"(_out) : : /* rax rbx rdx rsi rdi r8–r14, memory, cc */);

The microcode itself touches no memory — all 5 (or 10) input limbs arrive in architectural registers, all 5 result limbs leave in registers, and the wrapper does every load/store. This is the opposite of the Keccak design (which loads/stores inside the patch): here the operands are small enough to live entirely in the register file for the patch's whole lifetime.

1.3 Where fe_mul / fe_sq sit in X25519

X25519 is "scalar × point" on Curve25519, used for Diffie–Hellman. It runs a Montgomery ladder: 255 iterations, each one a ladderstep of 5 fe_mul + 4 fe_sq + 1 fe_mul121665 + ~10 fe_add/fe_sub, plus a final Fermat inversion (~265 field ops). Per call that is ≈ 2 300 multiply/square invocations — so field multiply and square are the entire hot loop. Everything else (the ladder driver, cswap, byte (de)serialization) is glue. Speeding up those two ops is the whole game.

1.4 The field, in 5×51 limbs

A field element is a 255-bit integer mod p = 2²⁵⁵ − 19, stored as 5 limbs of 51 bits in uint64_t[5] — unsaturated radix-2⁵¹ (the "Dettman/fiat" representation). Limb i carries weight 251·i; the spare 13 high bits per limb (64−51) absorb carries lazily, which is what lets addition skip a reduction. Two facts drive every line of the patch:

  • 2²⁵⁵ ≡ 19 (mod p). A product spills into limbs 5..8 (weights 2²⁵⁵ and up); folding them back means multiplying by 19 and adding into limbs 0..3. This is why the precomputed 19·bj values appear everywhere.
  • 2⁶⁴ = 2¹³ · 2⁵¹. The accumulator's "above 64 bits" overflow count (held in R8) contributes to the next limb's carry shifted left by exactly 13. This single arithmetic identity is the carry/link mechanism of §4.3.

1.5 The bet: the whole multiply lives in the register file

A 5×51 multiply is 25 (or, by squaring symmetry, 15) cross-products, each a 64×64→128 MUL, summed column-by-column with carries. Native code on x86-64 has ~14 GPRs and must juggle the 128-bit partial products, the running accumulator, and the carry chain through flags and spills. Microcode exposes a register file of 32 entries: GPRs 0x20–0x2f and TMP registers 0x30–0x3f. That headroom lets the entire accumulation — low accumulator, high accumulator, carry-sum, per-limb carries, mask scratch — stay resident, and lets a single triad issue a MUL and two accumulation ops together.

The thesis in one line Pack each 64×64 multiply-accumulate so its MUL, its low-half add, and its carry/high-half book-keeping share triads — and keep every accumulator in a register. Native code can't pack three dependent 64-bit ops into one issue group, and can't keep this many live carries without spilling; microcode can, and that density is the win — biggest for squaring, where there are only 15 MACs to begin with.

2.3 Hand-written, harness-verified

The Keccak patch is emitted by a self-verifying Python generator. The curve25519 patches are hand-written triad arrays — each is small and dense enough (42 / 66 triads) to author and reason about directly, and the carry algebra is fixed rather than parameterized over rounds. Correctness instead comes from a three-way differential harness baked into each file: every test runs an independent schoolbook reference, the native __uint128_t C, and the microcode, and asserts all three agree (§8.1). The accumulation pattern itself was lifted from a previously-proven patch (p521_sq's progressive accumulation), so the risky part — the carry chain — is reused, not reinvented.

3. Hardware facts (and how each shapes the code)

Every line of the patch obeys a fixed set of Goldmont microcode facts, established by the probe suite in simple/tests/ and recorded in CLAUDE.md. The load-bearing ones for field arithmetic:

3.1 Constraints → code

MUL_DSZ64_DRR(hi, srcA, srcB) semantics

A 64×64→128 multiply: srcA is preserved, srcB receives the low 64 bits, and hi receives the high 64 bits. So MUL(RCX, RDI, RDX) leaves RDI intact, puts the low product in RDX, the high in RCX. The patches exploit this constantly: the multiplier limb is loaded into the soon-to-be-overwritten RDX, and the surviving operand (ai) stays put for reuse.

MUL works in any slot

Confirmed by test_mul_slot2.c — a MUL is legal in slot 0, 1, or 2 of a triad. This is what lets PREP pack three ×19 MULs into one triad, and lets each MAC's MUL ride in slot 1 alongside an accumulate in slot 0 and a carry-add in slot 2.

Fully-sequential triads (RAW/WAR/WAW)

test_raw_war_waw.c proved every intra-triad hazard resolves sequentially for both arch and TMP regs: a later slot sees an earlier slot's write (RAW), an earlier reader sees the old value (WAR), and on a double-write the later slot wins (WAW). This is what the 88→66 / 43→42 packing rests on — e.g. {MUL RCX…; …; SHL TMP1, R8} where slot 2 reads the R8 that slot 0 just updated.

SETCC_CONDB_DR only on TMP registers

Capturing a carry-out bit (SETCC of the "below"/carry condition) works only into a TMP register, never an arch reg. So the carry chain is forced through TMPs: ADD TMP0,… then SETCC TMP15, TMP0. Result limbs are produced in TMPs and shifted out to arch regs at the end.

TMP registers don't persist across firings

TMP0–TMP15 are reset between vmwrite calls. Everything the patch needs must arrive in arch regs and leave in arch regs; TMPs are scratch only within one firing. (Irrelevant here since each field op is one firing, but it forbids caching anything between calls.)

ZEROEXT, not MOVE; even addresses

Register moves use ZEROEXT_DSZ64_DR (the generic MOVE form traps to a slow path). A zero is materialised with NOTAND(r,r,r) = ¬r ∧ r = 0. Patch base addresses must be even (0x7c00).

3.2 The flag-domain rule — why SETCC, never ADC

Two separate carry worlds Goldmont microcode has two flag domains. Domain #1 is per-TMP-register flags, set by ADD to a TMP and read by SETCC on that same TMP; it persists until the next ADD to that TMP. Domain #2 is the architectural RFLAGS that ADC reads — but it is frozen at patch entry and the bridge from #1→#2 (GENARITHFLAGS_R) fails unreliably in large patches. Consequence: the entire carry chain is built from ADD → SETCC(TMP) → ADD(+carry) triples. ADC is never used. See tests/adc_findings.md.

This is why a multiply-accumulate looks the way it does: you cannot say "add with carry." You add the low half into the accumulator, SETCC the carry into a TMP, and explicitly add that TMP into the next-higher accumulator. Each of those is one micro-op, and the trick is fitting all three into the triad of the MUL that produced the value.

4. The design

4.1 The MAC accumulator — one cross-product

Every limb ck is a sum of products Σ ai·bj. Each term is a 64×64→128 multiply whose 128-bit result must be added into a running sum that can exceed 64 bits. The patch keeps that running sum in three places:

RegisterHolds
TMP0low accumulator — the running 64-bit sum of low halves (mod 2⁶⁴).
R8high accumulator — the running sum of the products' high 64-bit halves.
TMP9carry-sum — the running count of carry-outs from the low-accumulator adds.
TMP15carry scratch — the single SETCC bit from the most recent ADD, before it is folded into TMP9.

The full 128-bit column sum is therefore (R8 + TMP9)·2⁶⁴ + TMP0. One MAC term, expanded:

MUL RCX = hi, RDX = lo   of  a_i × b_j     // srcA=a_i preserved, srcB=RDX←b_j gets lo
ADD TMP0 += RDX                          // low half into low accumulator
SETCC TMP15 = carry(TMP0)               // did that add overflow 2^64?
ADD R8   += RCX                          // high half into high accumulator
ADD TMP9 += TMP15                        // fold the carry into carry-sum

Five micro-ops per term — but they pack. The MUL of the next term goes in the same triad as the ADD R8/ADD TMP9 of the current one, so the steady-state cost is close to one triad per two micro-ops of useful work. The two alternating triad shapes are:

{ ADD TMP0 += RDX ,  SETCC TMP15 ,  ZEROEXT RDX = next_b }   // "ACC + prep" 
{ ADD R8 += RCX  ,  MUL RCX = a_i × RDX ,  ADD TMP9 += TMP15 }   // "hi + MAC + carry"

Notice the operand prep riding in slot 2 of the ACC triad: it loads the next multiplier limb into RDX (e.g. the next 19·bj) so the following MUL fires with zero setup latency.

4.2 Progressive accumulation (the p521_sq pattern)

The earlier, larger versions of these patches (88 triads for multiply) saved each MAC's high half and carry bit to separate TMP registers, then summed all of them at the end of the limb. That cost a register per term and a long tail of adds. The win, borrowed from the proven p521_sq patch, is progressive accumulation: fold each term's high half into R8 and each carry into TMP9 immediately, inside the MAC triad's free slot. No per-term storage, no tail — just two running registers that are already summed by the time the last MUL retires.

What it bought Multiply: 88 → 73 → 66 triads. Squaring: 43 → 42. The pattern collapses the "sum the partials" tail and frees the registers it used, which in turn enabled the cross-slot RAW/WAR packing tricks (§9.1).

4.3 The 51-bit carry and inter-limb link

After a limb's MAC sum is complete, its value is V = (R8 + TMP9)·2⁶⁴ + TMP0 (with R8 already holding R8+TMP9 after the finalize add). The output limb is V mod 2⁵¹ and the carry to the next limb is V div 2⁵¹. Using 2⁶⁴ = 2¹³·2⁵¹:

// output limb = low 51 bits of TMP0, via a shift pair (no AND-immediate needed)
SHL TMP_X = TMP0 << 13      SHR out = TMP_X >> 13      // = TMP0 & (2^51−1)
// carry to next limb = V >> 51 = (R8 << 13) | (TMP0 >> 51)
SHR TMP8 = TMP0 >> 51        // low part of the carry (≤13 bits)
SHL TMP1 = R8   << 13        // high part (R8 counts 2^64 overflows → bit 13+)
// next limb's first triad links them in:
OR  TMP0 = TMP8 | TMP1     // OR works because the two pieces don't overlap

The OR is valid (not just ADD) precisely because TMP0>>51 occupies ≤13 low bits and R8<<13 has zeros there — they tile without collision. This OR-link is the seam between consecutive limbs, and it absorbs what would otherwise be a separate "add the carry in" step into the start of the next limb for free.

4.4 Register allocation

The wrapper hands the patch its operands in fixed architectural registers and reads the results back from fixed registers. Multiply uses all five b limbs plus five a limbs; squaring pre-doubles and pre-reduces in the wrapper to exploit symmetry.

fe_sq — inputs & outputs

RDI=a0  RSI=a1  R12=a2  R11=a3  R14=a4
R15=2a0 R13=2a1 R9=2a2  R10=2a3      // doubled (wrapper lea)
RBX=19a4  RDX=19a3                   // reduced (wrapper imul)
RAX=0  R8=0                          // accumulators cleared
─ output ─
RDI=h0  R9=h1  R10=h2  RBX=h3  RAX=h4

fe_mul — inputs & outputs

RDI=a0  RSI=a1  R12=a2  R11=a3  R14=a4
R15=b0  R13=b1  R9=b2   R10=b3  RBX=b4
RAX=0  R8=0
─ after PREP (in-patch) ─
TMP10..14 = b0..b4 (saved)
R13=19b1 R9=19b2 R10=19b3 RBX=19b4
─ output ─
R15=h0  R13=h1  R9=h2  R10=h3  RAX=h4

Internal scratch (both patches): RCX = MUL high-half target; RDX = MUL low-half / next-multiplier; TMP0 = low accumulator; R8 = high accumulator; TMP9 = carry-sum; TMP15 = SETCC bit; TMP8 = lo carry-out; TMP1 = hi carry-out; TMP6/TMP2 = mask shift scratch.

5. The squaring patch, in execution order

5.1 Formula & triad map

fe_sq — the symmetric 15-MAC form 
# d_i = 2·a_i ;  r3 = 19·a3 ;  r4 = 19·a4  (precomputed in the wrapper)
c0 = a0·a0 + d1·r4 + d2·r3
c1 = d0·a1 + r3·a3 + d2·r4
c2 = d0·a2 + a1·a1 + d3·r4
c3 = d0·a3 + d1·a2 + r4·a4
c4 = d0·a4 + d1·a3 + a2·a2

Squaring is cheaper than multiply because ai·aj = aj·ai: the 25 cross-products collapse to 15 MACs (3 per limb) once the doubled limbs di account for the off-diagonal pairs. The wrapper precomputes di and r3,r4 with lea/imul so the patch only does MULs.

5.2 PREP — done in the wrapper, not the patch

wrapper asm_op_curve25519.c:271–311 (fe_sq_ucode)

Unlike multiply (whose PREP is 3 in-patch triads), squaring does its setup in the inline-asm wrapper, because the doubled/reduced limbs are pure arch-register arithmetic that the CPU's normal pipeline does for free before the patch fires:

mov rdi,[rcx] … mov r14,[rcx+32]   // load a0..a4
lea r15,[rdi+rdi]  lea r13,[rsi+rsi] … // 2·a0, 2·a1, 2·a2, 2·a3
imul rbx,r14,19   imul rdx,r11,19      // 19·a4, 19·a3
xor eax,eax  xor r8d,r8d            // clear accumulators
vmwrite rcx,rdx                       // fire

5.3 One limb in full — c0, 8 triads

triads asm_op_curve25519.c:59–92

c0 = a0·a0 + d1·r4 + d2·r3. Watch the three running registers (TMP0 low, R8 high, TMP9 carry-sum) fill, and the carry/link emerge in T5–T7:

T0 { ZEROEXT(TMP0,RAX),        MUL(RCX,RDI,RDI),    NOP }                 // TMP0=0; a0² → RCX:hi RDI:lo
T1 { ADD(TMP0,TMP0,RDI),       SETCC(TMP15,TMP0),   ADD(R8,R8,RCX) }       // MAC1: acc lo, carry, acc hi
T2 { ZEROEXT(TMP9,TMP15),      MUL(RCX,RBX,R13),    ADD(TMP0,TMP0,R13) }   // carry-sum init; MAC2 r4·d1; acc lo
T3 { SETCC(TMP15,TMP0),        ADD(R8,R8,RCX),      ADD(TMP9,TMP9,TMP15) } // MAC2 carry/hi folded
T4 { MUL(RCX,RDX,R9),          ADD(TMP0,TMP0,R9),   SETCC(TMP15,TMP0) }    // MAC3 r3·d2; acc lo; carry
T5 { ADD(R8,R8,RCX),           ADD(TMP9,TMP9,TMP15),SHR(TMP8,TMP0,51) }    // last hi/carry; lo carry-out
T6 { ADD(R8,R8,TMP9),          SHL(TMP6,TMP0,13),  SHL(TMP1,R8,13) }      // finalize hi; mask scratch; hi carry-out (s0→s2 RAW on R8)
T7 { SHR(RDI,TMP6,13),         ZEROEXT(R13,RSI),   NOTAND(R8,R8,R8) }     // h0=mask; prep a1 for c1; R8=0

Three things to see. (1) The carry-sum TMP9 is initialised by copying the first SETCC bit (T2 slot 0) rather than adding, saving an op. (2) T6 slot 2 reads the R8 that slot 0 wrote in the same triad — a slot-0→2 RAW, legal under §3.1. (3) T7 slot 1 preps the next limb's first operand (R13=a1) and slot 2 re-zeros R8 for the next limb, both in the otherwise-idle output triad.

Limbs c1, c2, c3 are the same 8-triad skeleton with different operands and different in-flight prep (e.g. c1 recomputes R9=2·a2 in T1, c3 rebuilds d1=2·a1 while RSI=a1 is still live). The link into each is the OR TMP0 = TMP8 | TMP1 in its T0.

5.4 c4 — the 8→7 packing

triads asm_op_curve25519.c:199–229

The last limb has no "next limb" to prep for, so its three idle prep/zero slots are reclaimed and the limb is compressed to 7 triads using the full sequential-hazard menu (the change that took the patch 43→42):

T3 { ADD(R8,R8,RCX), ADD(TMP9,TMP9,TMP15), MUL(RCX,R12,R12) }  // MAC3=a2² placed in slot 2 (s0→s2 WAR on RCX)
T4 { ADD(TMP0,TMP0,R12), SETCC(TMP15,TMP0), ADD(R8,R8,RCX) }   // consume that MAC's lo/carry/hi
T5 { ADD(TMP9,TMP9,TMP15), SHR(TMP8,TMP0,51), ADD(R8,R8,TMP9) } // finalize (s0→s2 RAW on TMP9)
T6 { SHL(TMP6,TMP0,13), SHL(TMP1,R8,13), SHR(RAX,TMP6,13) }     // mask + hi carry + h4 (s0→s2 RAW on TMP6)

The WAR on RCX in T3 (slot 0 reads the old MUL hi, slot 2 overwrites it with a fresh MUL) and the two slot-0→2 RAW chains in T5/T6 are exactly the hazards test_raw_war_waw.c certified, used here to erase three NOPs.

5.5 Final reduction — fold the top carry ×19

triads asm_op_curve25519.c:231–244

After c4 there is still a carry above limb 4 (weight ≥ 2²⁵⁵). Since 2²⁵⁵ ≡ 19, it folds back into limb 0 multiplied by 19:

F0 { OR(TMP0,TMP8,TMP1),  MUL(TMP6,19,TMP0),  ADD(RDI,RDI,TMP0) }  // full_carry; ×19 (s0→s1 RAW); h0 += 19·carry (s1→s2 RAW)
F1 { SHR(TMP0,RDI,51),    ADD(R9,R9,TMP0),    NOP }                // overflow from h0 into h1 (lazy)
F2 { SHL(TMP6,RDI,13),    SHR(RDI,TMP6,13),  NOP }   END           // mask h0 to 51 bits; return

F0 is a 3-deep dependency chain inside one triad: OR builds the carry, MUL reads it (slot 0→1 RAW), ADD reads the product (slot 1→2 RAW). H1 is left "lazily" ≤52 bits — legal because the next field op re-reduces, and the verifier explicitly checks no limb exceeds 52 bits.

6. The multiply patch, in execution order

6.1 Formula & triad map

fe_mul — schoolbook + 19-fold reduction 
c0 = a0·b0 + a1·19b4 + a2·19b3 + a3·19b2 + a4·19b1
c1 = a0·b1 + a1·b0   + a2·19b4 + a3·19b3 + a4·19b2
c2 = a0·b2 + a1·b1   + a2·b0   + a3·19b4 + a4·19b3
c3 = a0·b3 + a1·b2   + a2·b1   + a3·b0   + a4·19b4
c4 = a0·b4 + a1·b3   + a2·b2   + a3·b1   + a4·b0

No symmetry to exploit, so all 25 cross-products are computed — 5 MACs per limb. The wrap-around terms (anything that would land in limbs 5..8) are pre-multiplied by 19 so they fold straight into limbs 0..3.

6.2 PREP — 3 triads, 3 MULs in one

triads asm_op_curve25519_mul.c:97–111

The patch needs bj both raw (for c1..c4's straight terms) and ×19 (for the wrap terms), so it saves the raw values to TMPs first, then reduces the originals in place. P2 packs three ×19 MULs into one triad — legal because MUL works in any slot and the shared RCX high-half target is a WAW where the last write wins and is unused:

P0 { ZEROEXT(TMP10,R15), ZEROEXT(TMP11,R13), ZEROEXT(TMP12,R9) }   // save b0,b1,b2
P1 { ZEROEXT(TMP13,R10), ZEROEXT(TMP14,RBX), MUL(RCX,19,R13) }      // save b3,b4; R13=19·b1
P2 { MUL(RCX,19,R9),    MUL(RCX,19,R10),     MUL(RCX,19,RBX) }      // R9=19b2 R10=19b3 RBX=19b4

TMP0 init and the RDX=b0 seed for c0's first MAC are not done here — they were pushed down into c0's T0 to save the prep triads, an absorb that helped take the patch from 73 to 66.

6.3 One limb in full — c0, 12 triads

triads asm_op_curve25519_mul.c:113–163

Five MACs in the alternating "ACC+prep" / "hi+MAC+carry" cadence of §4.1. Each ACC triad's slot 2 preps the next multiplier into RDX, so every MUL fires with its operand already in place:

T0  { ZEROEXT(RDX,TMP10),    MUL(RCX,RDI,RDX),  NOTAND(TMP0,TMP0,TMP0) }  // RDX=b0; MAC1 a0·b0; TMP0=0 (s0→s1 RAW)
T1  { ADD(TMP0,TMP0,RDX),    SETCC(TMP15,TMP0), ZEROEXT(RDX,RBX) }       // acc lo; carry; prep RDX=19b4
T2  { ZEROEXT(R8,RCX),       MUL(RCX,RSI,RDX),  ZEROEXT(TMP9,TMP15) }     // R8=hi_1 (overwrite, no NOTAND); MAC2 a1·19b4; carry-sum init
T3  { ADD(TMP0,TMP0,RDX),    SETCC(TMP15,TMP0), ZEROEXT(RDX,R10) }       // acc lo; carry; prep RDX=19b3
T4  { ADD(R8,R8,RCX),        MUL(RCX,R12,RDX),  ADD(TMP9,TMP9,TMP15) }    // hi; MAC3 a2·19b3; carry fold
T5  { ADD(TMP0,TMP0,RDX),    SETCC(TMP15,TMP0), ZEROEXT(RDX,R9) }        // acc lo; carry; prep RDX=19b2
T6  { ADD(R8,R8,RCX),        MUL(RCX,R11,RDX),  ADD(TMP9,TMP9,TMP15) }    // hi; MAC4 a3·19b2; carry fold
T7  { ADD(TMP0,TMP0,RDX),    SETCC(TMP15,TMP0), ZEROEXT(RDX,R13) }       // acc lo; carry; prep RDX=19b1
T8  { ADD(R8,R8,RCX),        MUL(RCX,R14,RDX),  ADD(TMP9,TMP9,TMP15) }    // hi; MAC5 a4·19b1; carry fold
T9  { ADD(TMP0,TMP0,RDX),    SETCC(TMP15,TMP0), SHR(TMP8,TMP0,51) }       // last acc; carry; lo carry-out (s0→s2 RAW)
T10 { ADD(R8,R8,RCX),        ADD(TMP9,TMP9,TMP15),SHL(TMP2,TMP0,13) }     // last hi; last carry; mask scratch
T11 { ADD(R8,R8,TMP9),       SHR(R15,TMP2,13),  SHL(TMP1,R8,13) }        // finalize hi; h0=mask; hi carry-out (s0→s2 RAW)

The T2 trick is the cleanest packing in the patch: instead of ADD R8 += RCX (which would need R8 pre-zeroed by a NOTAND), the first high half is written with ZEROEXT R8 = RCX — overwriting whatever R8 held, which makes the per-limb R8-zeroing NOTAND unnecessary. That single substitution is one of the three changes that took the patch 73→66.

Limbs c1–c4 follow the identical 12-triad template; only the operand sequence and the OR-link (their T0 slot 2 instead of the NOTAND) differ. Each writes its result into the register the wrapper expects (R15,R13,R9,R10,RAX for h0..h4), reusing limb registers as they free up.

6.4 Final reduction

triads asm_op_curve25519_mul.c:370–386

Identical in shape to squaring's: fold the top carry ×19 into h0, propagate one carry into h1, mask h0.

F0 { OR(TMP0,TMP8,TMP1), MUL(TMP2,19,TMP0), ADD(R15,R15,TMP0) }   // 19·full_carry into h0 (3-deep RAW chain)
F1 { SHR(TMP0,R15,51),   ADD(R13,R13,TMP0),  NOP }              // h0 overflow → h1 (lazy ≤52 bits)
F2 { SHL(TMP2,R15,13),   SHR(R15,TMP2,13),  NOP }  END           // mask h0; return

Pin the core, and beware -fPIE The bench must run on core 0 (taskset -c 0) with the patch installed there. Like Keccak, any patch-installing target wants the static buffer in the low 4 GB; the harness pins the core and clears the hook on exit (init_match_and_patch). Frequency pinning to base (1.10 GHz) makes rdtsc ticks ≈ true cycles — see §8.2.

8. Verification & benchmarking

8.1 Three-way differential verification

Because there is no generator-simulator, correctness is proven on hardware by differential testing against two independent C implementations. Each harness defines:

  • fe_*_reference — a naïve schoolbook __uint128_t[9] accumulate-then-reduce, written for obviousness, not speed (the oracle).
  • fe_*_native — the optimised __uint128_t C that mirrors the patch's own formula (catches formula bugs).
  • fe_*_ucode — the microcode under test.

The verifier (verify_all) runs all three across: hand-checked known vectors (0, 1, 9, powers of 2⁵¹ that probe the 19-fold wrap, the basepoint), 10 000 random 5×51 inputs, and a 1 000-deep iterated chain from the basepoint (so any error compounds and is caught). It asserts reference == native == ucode bit-for-bit at every step, and additionally checks no output limb exceeds 52 bits (the lazy-carry invariant). Only if zero failures does it proceed to timing.

Why the chain test matters A single squaring that is off in one high bit can pass a one-shot test by luck. Feeding the output back in 1 000 times turns a one-in-a-million carry bug into a guaranteed, loud divergence from the reference chain — the same role the 64-vector sweep plays in the Keccak generator, done on hardware here.

8.2 The frequency trap

On Goldmont, rdtsc counts at a constant ~1.1 GHz reference rate, not the core clock (which bursts to ~2.4 GHz). The standalone harness measures all three implementations back-to-back in one process (BATCH=1000, REPS=100, report min and avg per op) so they share one frequency and the ratio is frequency-invariant. The SUPERCOP matrix additionally pins the core to base frequency so the absolute tick counts also read as true cycles. The number that matters is always the ratio microcode/fiat, never a raw tick count compared across runs.

9. Analysis

9.1 How the patches got small — the packing journey

Both patches started large and were compressed by exploiting the (later-certified) full sequential-hazard semantics of triads. The deltas, from the file headers:

PatchChangetriads
fe_mulNaïve: each MAC's hi/carry saved to its own TMP, summed at end88
fe_mulProgressive accumulation (p521_sq pattern): hi→R8, carry→TMP9 inside the MAC triad73
fe_mulPREP 6→3 (3 MULs/triad); per-limb prep absorbed into next limb's T0; NOTAND-zeroing of R8 replaced by ZEROEXT R8=RCX in T266
fe_sqPer-limb 8-triad skeleton with progressive accumulation43
fe_sqc4 packed 8→7 via cross-slot RAW/WAR/WAW (test_raw_war_waw.c)42

The throughline: the progressive accumulation idea did the heavy lifting (88→73), then the sequential-hazard packing certified by the probe suite squeezed out the NOPs (73→66, 43→42). None of these change the math — they change how many of the three slots in each triad do useful work.

9.2 Why squaring wins big and multiply barely

The structural reason fiat-crypto's C already compiles to tight mulx/adcx/adox on a normal core — but this is Goldmont, which has no fast ADX and a narrow multiplier. Microcode's edge is issuing a MUL plus two accumulation ops in one triad, with all carries in registers. Squaring has only 15 MACs, so the per-MAC packing dominates and the wrapper's lea/imul pre-work is cheap → a clear 26%. Multiply has 25 MACs and a 3-triad in-patch PREP (the ×19 reductions can't be hoisted to the wrapper as cheaply), so the fixed overhead is a larger fraction and the C baseline is closer → only 3%. In both cases the win is the per-MAC triad density that native register-starved code can't match.

There is also a real ceiling: microcode is latency-bound at roughly one triad/cycle, and a field multiply is a fundamentally serial carry chain. The patches are already near the floor of "one triad per two useful micro-ops"; further wins would have to come from the C-side wrapper (the ~15 cyc/call marshalling identified in design.md), not the patch.

9.3 Verdict

Two complete, correct, differentially-verified Curve25519 field operations run entirely in Goldmont microcode patch RAM — squaring in 42 triads at ~37 cyc (≈26% faster than fiat-crypto), multiply in 66 triads at ~58 cyc (≈3% faster), both far under the 128-triad cap. The win is built from one reusable idea — the MAC accumulator with progressive high/carry folding — packed into dense triads using the CPU's fully-sequential intra-triad semantics, and exploiting field-specific structure (radix-2⁵¹ carries via 2⁶⁴=2¹³·2⁵¹, the 19-fold wrap, and squaring symmetry). Dropped into the X25519 ladder (full_curve25519.c), these two patches are the accelerated core of an X25519 that is competitive with the fastest scalar field arithmetic on this hardware.
