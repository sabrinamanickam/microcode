1. Untangling the names

These four words get used interchangeably in conversation, but they are not the same thing. Here is the clean mental model:

NameWhat it actually is
KeccakThe original algorithm (a family), designed by Bertoni, Daemen, Peeters and Van Assche. It defines a permutation and a way to turn that permutation into a hash. This is the invention.
SHA-3The standard. In 2012 Keccak won NIST's public competition to choose the next hash standard; in 2015 NIST published it as SHA-3 in document FIPS 202. SHA-3 is Keccak, with a couple of small tweaks (mainly the padding — see §11).
Keccak-f[1600]The core engine: a fixed, reversible scrambling function (a permutation) that shuffles a 1600-bit block. Everything in this guide is mostly about this. The "1600" is the block size in bits.
SHAKEAn "extendable-output function" (XOF) built from the same engine. A normal hash gives a fixed number of output bits (256, 512…). SHAKE lets you ask for any number of output bits — useful when you need a stream of pseudorandom bytes.
One-line summary: Keccak is the recipe, SHA-3 is the official version of that recipe, Keccak-f[1600] is the scrambling engine inside it, and SHAKE is the variable-length-output flavor.

A historically important footnote: Keccak-256 (the pre-standardization version, with the original padding) is what Ethereum uses everywhere. It is not byte-for-byte identical to NIST's SHA3-256, even though both come from the same engine. The only difference is a few bits of padding. This is a frequent source of confusion.

2. Where it is used

  • General hashing. SHA-3 is a backup/alternative to SHA-2. Its internal design is completely different from SHA-2, so a future break of one is unlikely to affect the other.
  • Post-quantum cryptography. The new NIST standards built to resist quantum computers — ML-KEM (formerly Kyber), ML-DSA (Dilithium), SLH-DSA (SPHINCS+) — lean heavily on SHAKE128/256 for hashing and for generating pseudorandom matrices and noise.
  • Blockchains. Ethereum addresses, transaction hashes, and storage keys are Keccak-256.
  • Derived functions. NIST SP 800-185 defines cSHAKE, KMAC (a message authentication code), TupleHash and ParallelHash, all on top of the same engine.

3. The sponge construction

A hash function takes a message of any length and produces a short fixed digest. Keccak does this with a design called a sponge. The metaphor is literal: you absorb the message into a fixed-size internal memory, then squeeze the digest back out.

The internal memory is the state — for Keccak-f[1600] that's b = 1600 bits. The state is split into two conceptual parts:

b = r + c     // b = total state, r = rate, c = capacity 1600 = r + c
  • The rate r is the part that touches the message — how many message bits you mix in per step. Bigger r = faster.
  • The capacity c is the secret reserve that the message never directly touches. It is what gives the construction its security. The security level is roughly c / 2 bits.

So there is a direct speed-vs-security trade: a fixed 1600-bit budget split between r and c. Each SHA-3 variant just picks a different split (see §12).

Mechanically:

  1. Absorb. Cut the (padded) message into r-bit blocks. For each block: XOR it into the top r bits of the state, then run the permutation f on the whole 1600-bit state.
  2. Squeeze. Read off the top r bits as output. If you need more, run f again and read another r bits. Repeat until you have enough, then truncate to the requested length.

For a fixed hash like SHA3-256 you only ever read once and truncate. For SHAKE you keep squeezing as long as you like — that's the "extendable output."

4. The state: 1600 bits as a 5×5×64 cube

Inside the permutation, the 1600 bits are not treated as a flat array. They are arranged as a 3-D block of bits with coordinates (x, y, z):

A[x][y][z],   with   x ∈ {0,1,2,3,4},   y ∈ {0,1,2,3,4},   z ∈ {0,…,63} total bits = 5 × 5 × 64 = 1600

The z dimension is 64 because w = 64 is the lane width (one machine word). In general w = 2ℓ; for the 1600-bit version ℓ = 6, so w = 64. Smaller toy versions of Keccak exist (w = 1, 2, 4, … 32) but 1600 is the one used in practice.

Each named sub-piece of the cube has a term you'll see constantly in the spec:

NameWhat is fixedSize
Lanefix x and y, vary z64 bits (a full word)
Rowfix y and z, vary x5 bits
Columnfix x and z, vary y5 bits
Slicefix z, vary x and y25 bits (a 5×5 square)
Sheetfix x, vary y and z320 bits
Planefix y, vary x and z320 bits
Keep this in mind for every equation below: the x and y indices are always reduced mod 5, and the bit index z is always reduced mod 64. So x+1 when x=4 means 0, and a "rotate" wraps bits around the 64-bit lane.

5. The permutation Keccak-f[1600]

The engine f is just one function applied over and over. It runs for 24 rounds. The round count comes from the formula:

nr = 12 + 2ℓ    with ℓ = 6   →   nr = 12 + 12 = 24 rounds

Each round is the same five steps, applied in this fixed order:

Round(A, RC) = ι ∘ χ ∘ π ∘ ρ ∘ θ (A)   // read right-to-left: θ first, ι last

Each Greek letter is one transformation of the whole 1600-bit state. Their jobs, in one line each:

  • θ (theta) — mixes bits between columns, so each bit affects many others (diffusion).
  • ρ (rho) — rotates each lane by a fixed amount (spreads bits along z).
  • π (pi) — moves whole lanes to new positions (spreads bits across the slice).
  • χ (chi) — the only nonlinear step; it's what makes the function hard to invert algebraically.
  • ι (iota) — XORs in a round constant to break the symmetry that the other four steps would otherwise preserve.

θ, ρ, π and ι are all linear over the bits (XOR, rotate, move). χ is the single source of nonlinearity. That separation is deliberate and is the heart of the design.

6. Step 1 — θ (theta): column mixing

Plain idea: For each of the 5 columns of bits (a column has 5 bits along y), compute its parity — the XOR of all bits in it. Then add (XOR) into every bit a combination of two neighboring columns' parities. This makes each bit depend on bits in adjacent sheets, so a single bit flip quickly ripples outward.

The equations. First compute the parity of each column. C[x] is a 64-bit lane (one parity bit per z):

C[x] = A[x][0] ⊕ A[x][1] ⊕ A[x][2] ⊕ A[x][3] ⊕ A[x][4]     // for x = 0..4 ; this XORs the 5 lanes in sheet x

Then build the "to be added" lane D[x]. It takes the parity of the column to the left, and the parity of the column to the right rotated up by one bit:

D[x] = C[x−1] ⊕ ROT( C[x+1], 1 )     // x−1, x+1 mod 5 ; ROT(·,1) = rotate the 64-bit lane left by 1

Finally XOR D[x] into every lane of sheet x:

A′[x][y] = A[x][y] ⊕ D[x]   // for all y = 0..4

Per bit, written fully:

A′[x][y][z] = A[x][y][z]   ⊕ ( C[x−1][z] )   ⊕ ( C[x+1][z−1] )

7. Step 2 — ρ (rho): lane rotation

Plain idea: Take each of the 25 lanes and rotate its 64 bits by a fixed, per-lane offset. This is the step that mixes bits along the z-axis (within a word). Lane (0,0) is left alone (offset 0).

A′[x][y][z] = A[x][y][ (z − r[x][y]) mod 64 ]     // rotate the lane (x,y) by its offset r[x][y]

Where the offsets come from. They aren't arbitrary — they're generated by walking through the lanes in a fixed pattern and using triangular numbers:

offset for the t-th lane = ( (t+1)(t+2) / 2 ) mod 64,   t = 0..23 starting at (x,y) = (1,0), then (x,y) → ( y, (2x+3y) mod 5 )

That procedure produces this fixed table (rows = x, columns = y):

y=0y=1y=2y=3y=4
x=003634118
x=114410452
x=2626431561
x=32855252156
x=4272039814

Example: lane (2,3) gets rotated by 15 bits; lane (0,0) stays put.

8. Step 3 — π (pi): lane shuffle

Plain idea: Now move entire lanes to new (x,y) positions. ρ moved bits within lanes; π moves the lanes around the slice. The bit values are untouched — only their (x,y) addresses change.

A′[x][y][z] = A[ (x + 3y) mod 5 ][ x ][ z ]

Equivalently, stated as "where does the lane at (x,y) go": the lane originally at (x,y) lands at position (y, 2x+3y mod 5). Both phrasings describe the same permutation of the 25 lanes; the first (the one above, the FIPS 202 form) is the one you implement.

ρ and π together are sometimes thought of as one "ρπ" move: rotate each lane, then relocate it. After this pair, bits have been thoroughly spread in all three dimensions, but everything so far has been purely linear (just XORs and rearrangements). The next step adds the nonlinearity.

9. Step 4 — χ (chi): the nonlinear step

Plain idea: This is the only step that uses AND, not just XOR — and AND is what makes the function genuinely hard to invert with algebra. χ works on each row (5 bits across the x-direction) independently. Each output bit is its own value, XORed with the AND of its two neighbors to the "right" (one of them inverted).

A′[x][y][z] = A[x][y][z]   ⊕ ( ( NOT A[x+1][y][z] ) AND A[x+2][y][z] )     // x indices mod 5 ; done for every (y,z)

In words: "keep my bit, but flip it whenever the next bit is 0 and the bit after that is 1." Because of the AND, you cannot peel this apart with linear algebra — that nonlinearity is the cryptographic muscle of the whole round.

10. Step 5 — ι (iota): break the symmetry

Plain idea: The first four steps treat all the slices and lanes very symmetrically. That symmetry, if left alone, would create weaknesses (the rounds would all "look the same" and certain structured inputs would stay structured). ι fixes this by XORing a different constant into a single lane — lane (0,0) — on each of the 24 rounds.

A′[0][0] = A[0][0] ⊕ RC[i]   // only lane (0,0) changes; i = round number 0..23

The 24 round constants RC[i] are 64-bit values produced by a small LFSR (a linear-feedback shift register). They are fully fixed and public:

11. Padding & domain separation

Before absorbing, the message must be stretched to an exact multiple of r bits. Keccak uses multi-rate padding, written pad10*1: append a 1, then as many 0s as needed, then a final 1. The two end-1s guarantee the padding is never ambiguous and that every block is "full."

SHA-3 adds a few domain-separation bits in front of that padding so that different functions built on the same engine can never collide:

FunctionBits appended before pad10*1Resulting first padding byte
SHA3-224/256/384/512010x06
SHAKE128 / SHAKE25611110x1F
Original Keccak (e.g. Ethereum's Keccak-256)none0x01

The closing 1 of the padding shows up as the high bit 0x80 of the last byte of the block. This single difference — appended bits 01 vs nothing — is the entire reason NIST's SHA3-256 and Ethereum's Keccak-256 give different digests for the same input.

12. Parameter table for the SHA-3 family

Every variant uses the same 1600-bit engine. They differ only in how the 1600 bits split into rate vs capacity, how many bits they output, and the domain bits.

FunctionRate rCapacity cOutput bitsSecurity ≈ c/2
SHA3-2241152448224112
SHA3-2561088512256128
SHA3-384832768384192
SHA3-5125761024512256
SHAKE1281344256any length128
SHAKE2561088512any length256

Notice the pattern: for the fixed-length hashes, c = 2 × (output size), and as you ask for more security you spend more of the 1600-bit budget on capacity, leaving less rate, which is why SHA3-512 is slower than SHA3-256.

13. Putting it all together

Here is the whole thing, top to bottom, for (say) SHA3-256 hashing a message M:

  1. Pad. Append the domain bits 01, then pad10*1, so the total length is a multiple of r = 1088 bits.
  2. Initialize. Set the 1600-bit state to all zeros.
  3. Absorb. For each 1088-bit block: XOR it into the top 1088 bits of the state, then run Keccak-f[1600] — that is, run the 24 rounds, each round being
    ι ∘ χ ∘ π ∘ ρ ∘ θ
  4. Squeeze. Read the top 256 bits of the state. (Since 256 ≤ 1088, one squeeze is enough; no further permutation needed.) That's the digest.

And each single round, in full, is just these five lines applied to the cube:

θ: C[x] = ⊕y A[x][y] ;   D[x] = C[x−1] ⊕ ROT(C[x+1],1) ;   A[x][y] ⊕= D[x] ρ: A[x][y][z] = A[x][y][ z − r[x][y] ] π: A[x][y] = A[ x+3y ][ x ] χ: A[x][y] ⊕= ( ¬A[x+1][y] ) ∧ A[x+2][y] ι: A[0][0] ⊕= RC[round]
The mental picture to walk away with. Keccak takes 1600 bits arranged as a little 5×5×64 cube, and 24 times in a row it: (θ) smears each bit across neighboring columns, (ρ) twists every word, (π) reshuffles the words around the square, (χ) does the one genuinely nonlinear mash on each row, and (ι) stamps in a unique constant so no two rounds are identical. Wrap that engine in the absorb-and-squeeze sponge, choose your rate/capacity split, and you have SHA-3.

Authoritative reference for exact bit-ordering and test vectors: NIST FIPS PUB 202, "SHA-3 Standard: Permutation-Based Hash and Extendable-Output Functions" (2015), and the Keccak team's reference at keccak.team.
