Keccak-f[1600] in Goldmont Microcode

A complete technical rundown — from file structure to the last triad — of a full 24-round Keccak permutation encoded directly in Intel Goldmont microcode patch RAM, and benchmarked against the fastest hand-tuned scalar assembly.

0.934×
microcode / fastest SUPERCOP scalar

The looped 24-round permutation runs in 1910 cyc/perm versus 2045 cyc/perm for the fastest SUPERCOP scalar baseline (opt64lcu24), measured back-to-back in one process — a ~7% win. KAT-anchored at lane0 = 0xF1258F7940E1DDE7. 108 triads, inside the 128-triad patch-RAM cap.

This document explains the implementation in the directory simple/keccak/. The single source of truth is keccak_gen.py, a self-verifying generator that emits the microcode patch (keccak_perm_body.h) after proving it correct against a reference Keccak in a software simulator. Everything else — the harness, the benchmarks, the probes — exists to install, verify, and time that patch on real hardware.

The narrative has three threads, woven together below:

  1. Why the architecture is shaped the way it is — each decision and the hardware fact that forced it.
  2. A line-by-line read of the generated permutation in execution order, with the actual triads.
  3. How the win was actually built — the measured optimization deltas, the methodology, and the honest ceiling.

1. Background

1.1 What microcode patching is on this CPU

On this Goldmont CPU (Intel Atom family, Celeron N3350), microcode is patchable. Each x86 instruction is internally cracked into micro-ops (uops); some instructions execute a sequence of uops fetched from a small on-die patch RAM. The lib-micro infrastructure exposes two primitives:

  • patch_ucode(addr, patch, n) — write our own uops into patch RAM at U7c00…
  • hook_match_and_patch(slot, opcode, addr) — redirect an x86 instruction so executing it jumps into our uops.

Microcode is organized as triads: a unit of 3 micro-ops + 1 sequence word (the seqword controls flow — NOP_SEQWORD falls through, END_SEQWORD returns). One triad occupies 4 address units, hence the ×4 in address arithmetic. The usable region U7c00–U7dfc holds exactly 128 triads — the hard size cap for the entire permutation.

1.2 The vmwrite hook — the C↔microcode bridge

We hijack the vmwrite instruction (opcode 0x0cd8), which is meaningless in ordinary user code. Once hooked, every vmwrite rcx, rcx runs our microcode, with full access to the physical register file and memory. The bridge in C:

register uint64_t *_buf asm("rcx") = &g_keccak_buf[KECCAK_BASE_LANE];
asm volatile("vmwrite rcx, rcx\n\t"
    : "+r"(_buf) :
    : /* clobbers: every GPR the microcode trashes */
      "rax","rbx","rdx","rdi","rsi","rbp","r8"…"r15","memory","cc");

It pins the buffer pointer into RCX, fires the hooked vmwrite, and declares every GPR clobbered (the microcode trashes them all). The microcode reads and writes the state buffer through RCX.

1.3 Keccak-f[1600], in one round

Keccak-f[1600] is the permutation inside SHA-3. Its state is 25 lanes of 64 bits, indexed s[5·y + x] for x,y ∈ 0..4. A full permutation is 24 rounds; each round is five steps:

StepNameWhat it does
θ (theta)column parityC[x] = ⊕ of column x's 5 lanes; D[x] = C[x-1] ⊕ rol(C[x+1],1); XOR D[x] into every lane of column x.
ρ (rho)lane rotationrotate each lane left by a fixed per-lane amount RHO[i].
π (pi)lane permutationmove lane (x,y) to position (y, 2x+3y mod 5) — a renaming, no arithmetic.
χ (chi)nonlinear mixper row: out[x] = B[x] ⊕ ((¬B[x+1]) ∧ B[x+2]) — the only nonlinear step.
ι (iota)round constantXOR a round-specific constant RC[r] into lane (0,0).

The C reference (keccak_round_ref / keccak_perm_ref in both the harness and the generator) is the ground truth: the microcode must reproduce it bit-for-bit. The canonical self-test is the all-zero input, whose output lane 0 is the famous 0xF1258F7940E1DDE7.

1.4 The bet: register residency

Native x86-64 has ~14 usable GPRs, but Keccak's state is 25 lanes — so hand-written assembly spills to L1 constantly. Microcode exposes a register file of 32 entries: GPRs 0x20–0x2f and TMP registers 0x30–0x3f. That is enough to hold the entire 25-lane state resident across an entire round — even across all 24 rounds. This is a structural advantage native code cannot access, and the entire premise of the project.

The thesis in one line Load the 25 lanes once, run 24 rounds with the whole state living in registers, store once. Native asm achieves residency only by fully unrolling; we achieve it without unrolling — and use the freed register headroom for tricks (MOV-free χ, D-in-registers) that register-starved native code simply cannot do.

2.3 Generator-first, not hand-written

Nobody hand-writes 108 dense triads where a single mis-placed lane is a silent wrong answer and every hardware test risks hanging the box. Instead, keccak_gen.py emits an op-list IR, simulates it on a model that also models the hardware constraints (notably the 8-bit signed memory offset), asserts it matches the reference, and only then lowers it to triads. Correctness debugging happens in software — instant and safe — instead of on the fragile NUC.

3. Hardware facts (established by probes)

Every constraint below cost a crash, a segfault, or a misdiagnosis to discover, and is now hard-coded into the generator. Each was isolated by a dedicated probe in probes/.

3.1 The probes and what they found

ProbeQuestionFinding
probe_seg.cWhich microcode segment lets LDZX/STAD touch memory without hanging?SEG_DS (0x18) works. Other segment values hang the core so hard the watchdog can't fire — they crashed the whole NUC.
probe_offset.cHow does the 8-bit offset field in load/store behave — signed or unsigned?Offset is 8-bit signed (−128..+127 bytes = ±16 lanes). Beyond that it wraps/fails. → the base must be centered.
probe_index.cCan [base + index_reg] addressing reach beyond the immediate range?Yes — index-register form is full-width, no offset limit. Used for the RC table at lanes 32..55.
probe_rsp.cCan RSP be borrowed as a 32nd data register?Yes, if saved at entry and restored before the firing returns. (The microcode never touches the stack.)
probe_triad.cWhich intra-triad dependency patterns execute correctly?Intra-triad execution is fully sequential, including 3-deep RAW chains — dense 3-op packing is valid.
probe_stlf.cDoes store-to-load forwarding work within a patch?Yes (STLF works). Spilling C to the buffer and reloading is safe. Also re-confirmed the 3-deep RAW chain.
probe_loaduse.cIs there a load-use latency gap that returns zeros?No — the earlier "loads return 0" failures were offset-range violations, not latency. All load→use patterns pass.
probe_loop.cDo conditional/backward branches and indexed loads work for a counted loop?Forward CONDZ, indexed LDZX, and a backward counted loop all pass (accumulate 7×10 = 70). The XOR that sets ZF must share the triad with the UJMPCC.
probe_keccak_io.cHow many lanes can one patch load+store without hanging?Established the all-lanes I/O ceiling — full 25-lane load + store works. (≤1 memory op per triad throughout.)
probe_keccak_capacity.cHow many consecutive triads execute at U7c00 after init?128 triads — the full bank-0 region. (v1 hit a false wall at 120 by re-invoking the bootstrap each iteration; install the hook once up front and U7de0–U7dfc is reclaimable.)

3.2 How each constraint shapes the code

8-bit signed offset → centered base

Because offsets are −128..+127 bytes, the base register RCX points at the middle of the buffer: BASE_LANE = 16, so OFF(lane) = (lane−16)·8. Lane 0 → −128, lane 24 → +64, counter (lane 30) → +112, saved-RSP (lane 31) → +120 — all inside ±127. The RC table at lanes 32+ is out of immediate reach, so ι uses the index-register form instead.

≤1 memory op per triad

Two loads/stores in one triad hang the core (single L1 port). So the packer never places two memory ops in the same triad — the prologue and epilogue are therefore 25 separate single-load/single-store triads each.

MOVE_DSZ64 traps → use ZEROEXT

The generic MOVE form traps to a ~800k-cycle slow path. Register-to-register moves use ZEROEXT_DSZ64_DR; immediates use ZEROEXT_DSZ32_DI. The χ-cycle save-temp MOV lowers to ZEROEXT.

Fully-sequential triads → dense packing

A 3-deep RAW chain inside one triad is valid, and later slots see earlier slots' writes. This lets the packer fill all three slots even with dependent ops — crucial for the χ and apply phases.

Loop primitive → count up

UJMPCC...CONDNZ reads arch RFLAGS (ignoring its register operand), and an XOR in the same triad sets ZF. SUB-immediate is argument-reversed and ADD(−1) won't decrement on this microcode, so the counter counts up and compares via XOR idx, END.

32-register file → residency + RSP trick

25 lanes consume nearly all of GPR+TMP. The 5 resident D-values and the χ scratch need one more register, supplied by borrowing RSP (probe_rsp). This is the move that unlocked the win.

4. The design

4.1 The five decisions that define the implementation

Decision 1 — Loop all 24 rounds inside a single vmwrite

Each hook firing pays a fixed dispatch tax, and — critically — TMP registers do not persist across vmwrite calls. A per-round firing would be forced to round-trip all 25 lanes through memory every round; that memory traffic, not the arithmetic, would sink the design. So the entire permutation runs in one firing: 25 loads at the top, 24 rounds resident in registers, 25 stores at the bottom. The 50 I/O triads are paid once per permutation, not once per round. The loop is real (a backward branch), because 24× unrolling won't fit 128 triads.

Decision 2 — π is a permutation, so one looped body suffices

The worry with looping: π relabels lane positions every round, so "the lane in RDI" would drift. The resolution: π on the 25 lanes is a set of cycles — lane (0,0) is a fixed point, and the other 24 form a single 24-cycle. By applying π in place along its cycles (walk the cycle, move cyc[k-1] → cyc[k], with one save-temp for the head), every lane lands back in its canonical register slot at the end of each round. So round r+1 sees exactly the layout round r did, and one identical body loops 24× — no per-round renaming, no two-body trick.

Decision 3 — Generator-first (§2.3, §6)

Emit IR → simulate against the reference (with hardware constraints modeled) → lower to triads. Correctness is proven in software before hardware ever runs.

Decision 4 — Obey the hardware facts (§3)

Centered base, ≤1 mem/triad, SEG_DS, ZEROEXT not MOVE, count-up loop. These are not style choices; violating any one hangs or corrupts the machine.

Decision 5 — RSP as a 32nd register — the move that unlocked the win

The biggest structural lever was getting θ's five D-values to live in registers instead of being written to the buffer and re-read once per lane during the apply (25 extra memory triads per round). But 25 lanes already consume nearly all of GPR+TMP. probe_rsp proved RSP is usable as a 32nd data register if saved/restored once per perm. That freed the room for resident D and the χ scratch.

Why not rebuild the base instead? Earlier attempts freed a register by rebuilding the base RCX each round — and lost (2166, 2074 cyc): the rebuild cost more than the D-memory it saved. RSP wins precisely because RCX stays permanently pointed at the base — no rebuild.

4.2 Buffer layout

One contiguous array g_keccak_buf[56]; the base register RCX = &buf[16] is centered so every immediate offset fits the signed-8 field.

lane   offset(RCX)   contents
0..24   −128..+64    state      (resident in 13 GPR + 12 TMP during the round)
25..29  +72..+104    DSCR       θ-C parity scratch (5 lanes, spilled then re-read)
30      +112         COUNTER    RC byte-index (not a round number): init 128, += 8/round
31      +120         RSPSAVE    saved stack pointer (RSP borrowed as data reg)
32..55   far         RC[0..23]  round-constant table — index-register addressing only

The C wrapper fills state[0..24], sets COUNTER = (32−16)·8 = 128, and writes the RC table before each fire (reset_control). The loop end-marker is RC_END_IDX = 128 + 24·8 = 320.

5. The generated permutation, in execution order

5.1 Triad map

108 triads total, in three regions. The body is looped 24×; prologue and epilogue run once.

RegionTriadsAddressRunsWork
Prologue26U7c00…oncesave RSP + 25 lane loads
Body + loop-control56U7c68 (= loop_top)×24θ → ρ → π → χ → ι, then advance + branch
Epilogue26…once25 lane stores + restore RSP
load 25 lanes→ θ-C tree → buf→ θ-D → 5 regs→ θ-apply+ρ+π (in-place cycle)→ χ (MOV-free)→ ι (RC[idx])→ idx+=8; XOR/UJMPCC ↺→ store 25 lanes

Total triads issued per permutation: 26 + 56×24 + 26 = 1396. At the measured base-frequency cost that is ≈ 1.37 true cyc/triad (see §9.2).

5.2 Prologue — load state into registers (26 triads)

One store to save RSP, then 25 single-load triads (one per lane, because ≤1 mem op/triad). The first and last triads of keccak_perm_body.h:

{ STAD_DSZ64_ASZ32_SC1_RRI(RSP, RCX, 120, SEG_DS), NOP, NOP, NOP_SEQWORD }, // save RSP → buf[31]
{ LDZX_DSZ64_ASZ32_SC1_DRI(RDI, RCX, -128, SEG_DS), NOP, NOP, NOP_SEQWORD }, // lane0 → RDI
{ LDZX_DSZ64_ASZ32_SC1_DRI(RSI, RCX, -120, SEG_DS), NOP, NOP, NOP_SEQWORD }, // lane1 → RSI
… 25 loads, lane i → REG[i] …
{ LDZX_DSZ64_ASZ32_SC1_DRI(TMP11, RCX, 64, SEG_DS), NOP, NOP, NOP_SEQWORD }, // lane24 → TMP11

After this, lanes 0..24 in memory are not touched again until the epilogue. loop_top = U7c68 = 0x7c00 + 26·4 — the address right after the prologue is the branch target.

5.3 θ-C — balanced XOR tree → buffer (9 triads)

For each column x, C[x] = a^b^c^d^e of its five lanes. Instead of a depth-4 left chain, the generator emits a balanced tree of depth 3, using RSP as a second accumulator so the two halves compute in parallel:

XOR RAX = REG[x]    ^ REG[x+5]    // a^b
XOR RSP = REG[x+10] ^ REG[x+15]   // c^d   (independent — parallel)
XOR RAX = RAX ^ RSP               // (a^b)^(c^d)
XOR RAX = RAX ^ REG[x+20]         // ^e  → depth 3
ST  RAX → DSCR[x]                 // spill C[x] to buffer lane 25+x

Why this matters: C is the head of the round's dependency chain — every later phase waits on it. Shaving one level of latency off C shortens every round. C is written to the buffer (not kept in registers) because the registers are needed for resident D next, and C is read only a few times immediately after. Real lowered triads (note how the packer interleaves the store of one column with the start of the next):

{ XOR(RAX,RDI,R8), XOR(RSP,R13,TMP2), XOR(RAX,RAX,RSP), NOP_SEQWORD },
{ XOR(RAX,RAX,TMP7), STAD(RAX,RCX,72,SEG_DS), XOR(RAX,RSI,R9), NOP_SEQWORD },
{ XOR(RSP,R14,TMP3), XOR(RAX,RAX,RSP), XOR(RAX,RAX,TMP8), NOP_SEQWORD },
… columns 2,3,4 …

5.4 θ-D — into 5 registers, not the buffer (10 triads)

D[x] = C[x−1] ⊕ rol(C[x+1], 1). The five D-values land in registers D_REG = [RAX, TMP12, TMP13, TMP14, TMP15] and stay resident for the rest of the round. RSP is the rotate temp. No in-place hazard, because C is read from memory while D is written to registers:

LD  RSP      ← C[(x+1)%5]    // from DSCR buffer
ROL RSP, 1
LD  D_REG[x] ← C[(x+4)%5]    // = C[x−1]
XOR D_REG[x] = D_REG[x] ^ RSP

This is the part Decision 5 made affordable: without the borrowed RSP register, D had to go back to the buffer and be re-loaded per lane — the +25 memory-triads/round that earlier versions paid.

5.5 θ-apply + ρ + π — in place, D read from registers (17 triads)

This is the heart of the round, and where Decision 2 pays off. Walk π's single 24-cycle (lane 0 is the fixed point, handled inline). For the cycle, save the head into RSP, then shift each element to its π-destination, folding in θ (^ D_REG[col(src)]) and ρ (ROL by RHO[src]) as we go:

MOV RSP = REG[cyc[L-1]]                         // save cycle head (lowers to ZEROEXT)
for k = L-1 … 1:
    XOR REG[cyc[k]] = REG[cyc[k-1]] ^ D_REG[col(cyc[k-1])]
    ROL REG[cyc[k]] by RHO[cyc[k-1]]
XOR REG[cyc[0]] = RSP ^ D_REG[col(cyc[L-1])]      // close the cycle from the saved head
ROL REG[cyc[0]] by RHO[cyc[L-1]]

Two things to notice. First, D is read straight from registers — there is no per-lane load, which is exactly the win. Second, because we move along the cycle, every lane lands in its canonical register slot, so the layout is preserved for the next round. The lowered triads pack a θ-XOR and a ρ-ROL together (the fixed point + cycle head start on the same triad):

{ XOR(TMP15,TMP15,RSP), XOR(RDI,RDI,RAX), ZEROEXT(RSP,R9), NOP_SEQWORD },  // lane0 apply (RHO=0) + save head
{ XOR(R9,R12,TMP15), ROL(R9,R9,20), XOR(R12,TMP9,TMP13), NOP_SEQWORD },
{ ROL(R12,R12,61), XOR(TMP9,TMP1,TMP15), ROL(TMP9,TMP9,39), NOP_SEQWORD },
… the full 24-cycle, two lanes per triad …

5.6 χ — MOV-free, using the dead D-registers as scratch (17 triads)

χ is s[x] ^= ¬s[x+1] & s[x+2] across each row of 5. Done naïvely in place, the first lane you overwrite is still needed by later lanes, forcing save-MOVs — register-starved native code pays ~2 MOVs/row = 10/round. We have headroom (the five D-registers are dead now), so the generator computes all 5 NOTANDs of the row first into the freed registers, then does 5 in-place XORs:

SCR5 = [RAX, TMP12, TMP13, TMP14, TMP15]   // the now-dead D regs
for x in 0..4:  NOTAND SCR5[x] = (¬REG[r[x+1]]) ∧ REG[r[x+2]]   // B still intact
for x in 0..4:  XOR    REG[r[x]] = REG[r[x]] ^ SCR5[x]
{ NOTAND(RAX,RSI,RBX), NOTAND(TMP12,RBX,RDX), NOTAND(TMP13,RDX,RBP), NOP_SEQWORD },
{ NOTAND(TMP14,RBP,RDI), NOTAND(TMP15,RDI,RSI), XOR(RDI,RDI,RAX), NOP_SEQWORD },
{ XOR(RSI,RSI,TMP12), XOR(RBX,RBX,TMP13), XOR(RDX,RDX,TMP14), NOP_SEQWORD },
… 5 rows …

No save-MOVs at all. This is something native cannot do — it has no spare registers. Our register residency directly buys it; it was the single biggest measured jump (~5%, §9.1).

5.7 ι — round constant via byte-indexed table

The subtle optimization: the COUNTER lane stores the byte offset of the current RC directly (init 128, += 8/round), so fetching RC is just load-index, indexed-load, XOR — no SHL/ADD on the ι→RC→lane0 critical path. The RC table at lanes 32..55 is past the immediate range, so ι uses the index-register LDX form:

LD  TMP14 ← COUNTER          // the RC byte-index
LDX TMP13 ← mem[RCX + TMP14]  // index-register form: RC = table[idx]
XOR REG[0] = REG[0] ^ TMP13   // ι into lane 0
{ XOR(TMP10,TMP10,TMP14), XOR(TMP11,TMP11,TMP15), LDZX(TMP14,RCX,112,SEG_DS), NOP_SEQWORD }, // load idx (folded into χ tail)
{ LDZX_…_DRR(TMP13, RCX, TMP14, SEG_DS), NOP, NOP, NOP_SEQWORD },                       // indexed RC fetch
{ XOR(RDI,RDI,TMP13), ADD(TMP14,TMP14,8), STAD(TMP14,RCX,112,SEG_DS), NOP_SEQWORD },        // ι + advance idx + persist

5.8 Loop control — the backward branch

The +=8 arithmetic is paid here (off the ι critical path). Then a single forced triad does the branch: an XOR sets ZF in the same triad as the UJMPCC:

{ XOR_DSZ64_DRI(TMP12, TMP14, 320), NOP,
  UJMPCC_DIRECT_NOTTAKEN_CONDNZ_RI(TMP12, 0x7c68), NOP_SEQWORD },

320 = RC_END_IDX = the byte-index just past RC[23]. The XOR computes idx ^ 320; while idx ≠ 320 the result is non-zero, ZF is clear, and the UJMPCC...CONDNZ branches back to loop_top = 0x7c68. When idx == 320, the XOR yields 0, ZF is set, the branch is not taken, and control falls through to the epilogue — exactly 24 iterations. We count up because decrement-style ops don't work on this microcode (§3.2).

5.9 Epilogue — store state, restore RSP (26 triads)

for i in 0..24:  ST REG[i] → OFF(i)     // write the 25 lanes back to the buffer
LD RSP ← RSPSAVE                    // restore the stack pointer before returning

The final LD RSP ends with END_SEQWORD, returning control to the C side cleanly — which is exactly what probe_rsp verified is safe.

6. The generator (keccak_gen.py)

6.1 IR → simulate → pack → lower to C

The generator is a small compiler. The stages:

StageFunction(s)What it does
1. Emit IRgen_prologue, gen_body, gen_loopctrl, gen_epilogueProduce an ordered op-list using a tiny IR: LD/ST/LDX/STX/XOR/XORI/ROL/NOTAND/MOV/ADDI/SHLI/LOOPTEST with real register names.
2. Simulatesimulate_permRun the op-list on a register-file + 56-lane memory model that enforces the 8-bit signed offset (at(off) asserts −128..127) and resolves index-register loads. Drives the 24-round loop in Python.
3. Verifyverify_perm(64)Assert the simulator output equals keccak_perm_ref for 64/64 random states. Exit with an error if any lane mismatches.
4. PackpackGreedily chunk the op-list into triads: ≤3 ops, ≤1 memory op, no load-to-use within a triad, and LOOPTEST forced into its own triad.
5. Lowerop_to_c, emit_perm_cMap each IR op to a ucode_macro.h macro and write keccak_perm.h + keccak_perm_body.h, computing loop_top from the prologue length.

The IR → macro mapping is direct: LD → LDZX_DSZ64_ASZ32_SC1_DRI (immediate offset), LDX → ..._DRR (index register), ST → STAD_..._RRI, XOR → XOR_DSZ64_DRR, ROL → ROL_DSZ64_DRI, NOTAND → NOTAND_DSZ64_DRR, MOV → ZEROEXT_DSZ64_DR, ADDI → ADD_DSZ64_DRI. LOOPTEST expands to the XOR + NOP + UJMPCC triad shown in §5.8.

6.2 Why simulating first is non-negotiable

Caught in software, not on the box The simulator's at(off) assertion models the exact hardware addressing limit. An earlier buffer design put scratch at offsets ≥ 256, which on hardware silently wrapped and corrupted the state — and had previously crashed the NUC and been misdiagnosed as a "RAW dependency" failure. Modeling the constraint in the simulator turns a hardware crash into a Python AssertionError. Every design change is validated against 64 reference vectors before it ever touches patch RAM.

Running python3 keccak_gen.py prints PERM SIM OK: 64/64 … and the triad budget (perm triads=108 (prologue 26 + body+loop 56 + epilogue 26) cap 128), then regenerates the two headers.

7. Build & run

7.1 Makefiles and the flags that matter

Two Makefiles: the top-level keccak/Makefile builds the implementation harness; keccak/bench/Makefile builds the benchmarks and compiles the SUPERCOP scalar baselines.

# regenerate the patch (verifies 64/64 first)
$ python3 keccak_gen.py

# build + KAT-verify on hardware
$ make PROG=asm_op_keccak_perm
$ sudo taskset -c 0 ./asm_op_keccak_perm_static

# head-to-head benchmark vs all SUPERCOP scalar variants
$ cd bench && make PROG=asm_op_keccak_vs
$ sudo taskset -c 0 ./asm_op_keccak_vs_static

# full compiler × -O sweep → KECCAK_RESULTS.md
$ cd bench && sudo ./bench_keccak_matrix.sh
Critical flag: -no-pie LDZX_DSZ64_ASZ32 only takes 32-bit addresses (only the ASZ32 form exists). Under -fPIE, the static g_keccak_buf can land above 4 GB and the microcode loads garbage. The Makefile filters out -fPIE and forces -no-pie for any patch-installing target, pinning the buffer into the low 4 GB. The harness also checks g_keccak_buf < 0x100000000 at startup and aborts if not.

The SUPERCOP baselines are compiled from supercop-20260330/crypto_hash/keccakc1024/ and renamed via objcopy --redefine-sym so the four variants (and the microcode) coexist in one binary. The hand-written .s variants assemble identically at every config; only the C variants (opt64lcu24) are actually tuned by the compiler grid.

8. Benchmarking & methodology

8.1 The frequency trap (why naïve timing lies)

On Goldmont, rdtsc counts at a constant reference rate (~1.1 GHz), not the core clock. The core bursts to ~2.4 GHz under load. So the same work reads as ~2.2× fewer or more rdtsc ticks depending on the P-state during measurement. Measuring two implementations in separate runs — or comparing a fresh number against a baseline captured at a different frequency — is invalid.

The trap, concretely asm_op_keccak_perm.c's built-in bench() prints "baseline x86_64_asm: 939 cyc" (a number captured standalone at base frequency) and compares the microcode's freshly-measured ticks against it. Because the microcode bench runs at burst frequency, it reads ~1900–2000 ticks and reports "(loss)" — even though the implementation actually wins. That comparison is kept only as a rough sanity timer; the verdict comes from asm_op_keccak_vs.c. This exact confusion is why Phase 4 first recorded a "2.2× loss" before the methodology was fixed.

8.2 The valid harness — asm_op_keccak_vs.c

The fix: time the microcode and all four SUPERCOP scalar variants back-to-back, interleaved, in one process, after a warmup loop drives the core to steady frequency. Both see the same frequency, so the ratio is frequency-invariant. Per-rep batches of 1000 calls × 200 reps; report the median and a robust min (skip implausible near-zero batches caused by a P-state transition straddling the rdtsc bracket).

It also benchmarks the right competitor. The four scalar contenders:

  • x86_64_asm (Van Keer, ROL) — 942 cyc, the fastest
  • opt64lcu24 (C, 24× unroll, bebigokimisa) — 979 cyc
  • x86_64_shld and opt64lcu24shld — ≈ 4630 cyc (SHLD is catastrophic on Goldmont/Atom)

So the win is measured against the genuinely fastest scalar implementation, not a strawman.

8.3 The compiler matrix — bench_keccak_matrix.sh

SUPERCOP's autotuner picks the best result across many compiler/-O configs. To match that, the matrix rebuilds the head-to-head under 24 configs (gcc-11/12/13 and clang-14/17/18 × -O3/-O2/-Os/-O) and keeps the best per contender. A frequency guard pins to base first so absolute ticks ≈ true cycles; the same-process ratio inside each run stays valid regardless.

9. Analysis

9.1 How the win was built — measured deltas

The optimizations were empirical, each measured back-to-back in the same process. The win is the product of four steps, each attacking the round's critical path or exploiting register headroom native lacks:

StepChangeratioNote
0Per-lane D in buffer, naïve χ with save-MOVs1.00×Correct but only a tie; looked D-memory-bound.
1D resident in registers via the RSP 32nd-register trick (no RCX rebuild)0.99×Small directly, but freed the path to step 2.
2MOV-free χ using the dead D-registers as NOTAND scratch0.95×The biggest single jump (~5%) — the clearest "register headroom native lacks."
3θ balanced XOR tree (depth 4→3) + RC byte-index (no SHL/ADD on the ι path)0.93×The final ~7% — both shorten the critical path (C is the chain head; ι feeds lane 0).

9.2 The latency model — why the gain is only ~7%

Per-triad cost has two faces. A single isolated firing measured 0.49 cyc/triad — but that is a throughput figure: 1000 independent vmwrites that the out-of-order engine overlaps heavily. The looped permutation is a hard dependency chain (round N needs round N−1) with a per-round backward branch, so it pays true latency with no inter-call overlap: ≈ 1.37 true cyc/triad (1396 triads → ~1910 cyc).

The structural ceiling Microcode is latency-bound at roughly 1 triad/cycle. SUPERCOP's x86_64_asm does ~3 ops/cycle via BMI/rotate ILP. The register-residency advantage (no per-round spills) is real but does not blow the doors off, because θ→ρ→π→χ is an inherently sequential chain — each trick buys only a few percent, and we can't unroll for more parallelism because of the 128-triad patch-RAM cap. The win comes entirely from doing per-round work native can't: full register residency (state I/O paid once per perm), a free 32nd register, and MOV-free χ.

9.4 Verdict

A complete, correct, KAT-verified 24-round Keccak-f[1600] runs entirely in Goldmont microcode patch RAM, looped inside one vmwrite firing, in 108 triads (20 under the cap). Benchmarked honestly — back-to-back, same frequency, against the genuinely fastest scalar baseline — it runs at 0.934×, a ~7% win. The margin is modest by design: Keccak is chain-bound and microcode is latency-bound, so the only available edge is the per-round work that native register-starvation forbids — and that edge, fully exploited (residency, the borrowed 32nd register, MOV-free χ, a depth-3 parity tree, and a critical-path-free round constant), is exactly enough to win.
