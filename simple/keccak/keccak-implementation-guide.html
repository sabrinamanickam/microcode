The companion guide explains the math (θ ρ π χ ι on a 5×5×64 cube). This explains how we encode that exact math directly as Intel Goldmont CPU microcode, run all 24 rounds inside one trapped instruction, and beat the fastest hand-tuned SUPERCOP assembly.

1. What we built & the headline result

The engine from the companion guide's §5 — Keccak‑f[1600], 24 rounds of ι ∘ χ ∘ π ∘ ρ ∘ θ — is implemented here not as compiled C or even hand assembly, but as a patch loaded into the CPU's internal microcode RAM. One ordinary-looking machine instruction is hijacked so that executing it runs the entire 24-round permutation in place.

Result (Intel Celeron N3350, Goldmont). The microcode permutation is correct — KAT-anchored at lane 0 = 0xF1258F7940E1DDE7 for the all-zero input — and ~6–7% faster than the fastest scalar Keccak in SUPERCOP. The win is a ratio (≈ 0.93, microcode ÷ fastest baseline), measured back-to-back in one process so it is independent of CPU frequency. At base-pinned frequency that is roughly 1900 cyc/perm for microcode vs ~2045 for the best SUPERCOP variant (see §12 for why the absolute number depends on pinning).

Everything in this implementation is generated and software-verified by keccak_gen.py (the D_IN_REGS path), which emits the triad table keccak_perm_body.h and asserts it matches the reference permutation on 64 test vectors before it ever touches hardware.

2. The mechanism: what "microcode" means here

An x86 instruction is itself carried out by a sequence of tiny internal operations — micro-ops — drawn from the CPU's microcode. Goldmont lets us patch that microcode RAM and hook a chosen instruction. We pick the rarely-used vmwrite: after patching, executing vmwrite rcx, rcx runs our permutation, with rcx pointing at the state in memory.

A patch is an array of triads. Each triad is three micro-ops plus a seqword that controls flow (continue, branch, or end):

Two facts from this picture drive the entire design: micro-ops within a triad execute in sequence (so a 3-deep dependency chain works inside one triad), and the patch can hold only 128 triads. The second is why we cannot simply unroll 24 rounds — we must loop.

3. The plan: the cube must live in registers

The companion guide's §4 lays the 1600 bits out as 25 lanes, each a 64-bit word. The naive way to port this is one trapped call per round. That is fatal for two reasons: the trap does not preserve our working registers across calls, and each Greek step would then have to reload and re-store all 25 lanes from memory every round. Memory traffic — not arithmetic — would dominate.

So we do what hand-tuned assembly does when it unrolls: keep the whole cube resident in registers. We load the 25 lanes once at the top, run all 24 rounds entirely in the register file, and store once at the bottom. Because we cannot unroll (128-triad limit), the 24 rounds are a real loop.

permutation — never per round. That is the whole source of the speed.

The 25 lanes map to named registers as follows (lane i = x + 5y, from the guide's indexing):

lanesregister(s)role
0 – 12RDI RSI RBX RDX RBP R8 R9 R10 R11 R12 R13 R14 R1513 general-purpose registers
13 – 24TMP0 … TMP1112 microcode temporaries

The other registers do double duty: RCX is the base pointer to the state buffer; RAX and TMP12–TMP15 hold θ's D values and then χ's scratch; RSP is borrowed as a 32nd data register (see §5).

4. The problem looping creates — and why π solves it

Looping a single round body has a subtle hazard. The companion guide's §8 π step relocates whole lanes to new (x,y) positions every round. If our lanes sit in fixed registers, then after round 1 the register that held lane (0,0) now holds some other logical lane — and round 2's θ would read the wrong words. A naive loop would be wrong.

The rescue is a property of π itself: as a permutation of the 25 lane positions it is a set of cycles, with lane (0,0) fixed. We apply π in place along those cycles (walking each cycle, moving each lane to its destination with a single save-temp for the cycle's head). When the walk finishes, every lane is back in its canonical register slot. So round r+1 sees exactly the register layout round r did — and one identical body can loop 24 times correctly.

This is the linchpin of the whole approach: π making the layout self-restoring is what lets us loop instead of unroll, which is what lets us fit inside 128 triads.

5. The register budget & the 32nd register (RSP)

The integer register file is exactly 32 (16 GPR 0x20–0x2f + 16 TMP 0x30–0x3f). Twenty-five are spent on lanes. θ needs to keep its five D values resident and a save-temp for the π cycle walk — one register more than is free.

We found the missing register in RSP, the stack pointer. Our microcode never touches the stack, so if we save RSP at entry and restore it before the trap returns, RSP is a usable 32nd data register for the whole permutation. (An earlier idea — freeing a register by rebuilding the base pointer each round — measured slower: the rebuild cost more than it saved. RSP wins because the base pointer RCX never moves.)

The state buffer carries a little scratch beyond the 25 lanes. Because the load/store offset field is only 8-bit signed (±127 bytes = ±15 lanes), the base pointer is centered at lane 16, so offset(lane) = (lane − 16) × 8 stays in range:

buffer lanescontentsoffset from base (lane 16)

25 – 29θ column-parity scratch (C[x])+72 … +104

32 – 55the 24 round constants RC[0..23]+128 … (out of range → indexed load)

The RC table sits beyond the signed-8 reach on purpose; ι reaches it with an index register instead (see §9).

6. θ in microcode — balanced parity tree + D in registers

The companion guide's §6 gives θ in three equations: column parities C[x], the mixing lane D[x], then XOR D[x] into the sheet. We realize them in two moves.

(a) Column parities, as a balanced XOR tree. C[x] is the XOR of the five lanes in sheet x. The obvious encoding is a 4-deep chain; instead we compute it as a depth-3 balanced tree, because C sits at the head of the round's dependency chain — every later step waits on it, so shortening its latency shortens every round. RSP (free here) is the second accumulator:

// companion §6: C[x] = A[x][0]⊕A[x][1]⊕A[x][2]⊕A[x][3]⊕A[x][4] RAX = REG[x] ⊕ REG[x+5] // a ⊕ b RSP = REG[x+10] ⊕ REG[x+15] // c ⊕ d (independent — runs in parallel) RAX = RAX ⊕ RSP // (a⊕b) ⊕ (c⊕d) RAX = RAX ⊕ REG[x+20] // ⊕ e → depth 3, not 4 store RAX → C[x] scratch lane // for x = 0..4

(b) The mixing lane D[x], computed straight into registers. The guide's D[x] = C[x−1] ⊕ ROT(C[x+1], 1) would normally be written to memory and re-read once per lane during the apply — 25 extra loads per round. With our 32nd register we keep all five D values live in registers (D_REG = RAX, TMP12, TMP13, TMP14, TMP15), using RSP as the rotate temp:

// companion §6: D[x] = C[x−1] ⊕ ROT(C[x+1], 1) RSP = C[x+1] scratch // load right neighbor parity RSP = ROL(RSP, 1) // ROT(·,1) D_REG[x] = C[x−1] scratch // load left neighbor parity D_REG[x] = D_REG[x] ⊕ RSP // D[x], now resident in a register
Keeping D in registers removes ~25 memory loads per round. It is only affordable because RSP gave us the 32nd register (§5). This single change is what unlocked the win.

7. ρ and π in microcode — one in-place cycle walk

The companion guide treats §7 ρ (rotate each lane by a fixed per-lane offset) and §8 π (relocate lanes) as separate steps, and notes they're often fused into one "ρπ" move. We fuse all three of θ-apply + ρ + π into a single in-place pass over π's cycles. For each cycle we save its head lane in RSP, then shift each lane to its π destination while folding in θ's D (an XOR) and ρ's rotation (a ROL by the offset table):

// for each π cycle (lane (0,0) is a fixed point): RSP = REG[head] // save the lane that would be overwritten for each step src → dst along the cycle: REG[dst] = REG[src] ⊕ D_REG[src mod 5] // θ-apply: A[x][y] ⊕ D[x] REG[dst] = ROL(REG[dst], RHO[src]) // ρ: rotate by the per-lane offset close the cycle using RSP for the head lane

Two things make this fast. D is read straight from D_REG[...] — no per-lane memory load (the payoff of §6b). And because the moves follow π's cycles, every lane lands back in its canonical register slot, preserving the layout for the next round (§4). The rotation amounts RHO[i] are exactly the offset table in the companion guide's §7, indexed by i = x + 5y.

8. χ in microcode — the MOV-free nonlinear step

The companion guide's §9 χ is the only nonlinear step: per 5-bit row, A[x] ⊕= (¬A[x+1]) ∧ A[x+2]. Done in place, the early lanes you overwrite are still needed by later lanes in the same row — so register-starved native code is forced into save-copies (≈2 MOVs per row, ~10 per round).

We have spare registers (the five D_REG are dead after θ), so we sidestep the copies entirely: compute all five row NOTANDs into the freed registers first, while the original row values are still intact, then do five in-place XORs:

// per row y = 0..4 ; SCR5 = the now-dead D registers (RAX, TMP12..TMP15) for x = 0..4: SCR5[x] = (¬REG[row(x+1)]) ∧ REG[row(x+2)] // companion §9, all 5 first for x = 0..4: REG[row(x)] = REG[row(x)] ⊕ SCR5[x] // then 5 in-place XORs
This is a concrete example of our register advantage: native assembly cannot do this on Goldmont because it has no spare registers — it must spend MOVs. We don't, because the cube is fully register-resident.

9. ι in microcode — byte-indexed round constants

The companion guide's §10 ι XORs a round-specific constant into lane (0,0): A[0][0] ⊕= RC[round]. The 24 constants live in a table in the state buffer (lanes 32–55). The trick is in addressing it: the counter lane holds the constant's byte offset directly (initialized to 128, advanced by 8 each round), so fetching the constant costs nothing extra on the critical path:

TMP14 = counter lane // the RC byte-index (not a round number) TMP13 = mem[ base + TMP14 ] // indexed load: RC[round], reaches the far table REG[0] = REG[0] ⊕ TMP13 // companion §10: A[0][0] ⊕= RC[round]

There is no shift or add on the ι → RC → lane 0 path; the +8 increment is paid later, in the loop-control step (§10), off the critical path. The indexed load is also how we reach the RC table at all — it lies beyond the 8-bit signed offset window (§5).

10. The 24-round loop inside one vmwrite

The companion guide's §5 says the engine is 24 identical rounds. We close the loop with a single control triad: advance the RC byte-index, store it, then test-and-branch. The compare-and-branch share one triad — the XOR sets the zero flag and the conditional branch reads it in the same triad:

TMP14 = TMP14 + 8 // advance RC byte-index store TMP14 → counter lane TMP12 = TMP14 ⊕ 320 ; UJMPCC CONDNZ → loop_top // 320 = byte-index past RC[23]

We count up to 320 (the hardware's subtract-immediate is awkward, so counting up is cheapest). When the index reaches 320 the XOR yields zero, the zero flag is set, the branch is not taken, and control falls through to the epilogue. That is exactly 24 iterations.

The full patch is 108 triads, comfortably under the 128 cap:

sectiontriadswhat it does
prologue26save RSP, load the 25 lanes (once per permutation)
round body + loop control56θ ρ π χ ι + the backward branch (runs 24×)
epilogue26store the 25 lanes, restore RSP (once per permutation)
We loop rather than unroll for one hard reason: 24 copies of the body would need far more than 128 triads. Looping trades a tiny per-round branch cost for fitting in patch RAM at all.

11. How we made it fast

Keccak is dependency-chain bound (θ → ρ → π → χ in sequence), so no single trick is dramatic; the win is the sum of several, each shaving the critical path. We measured each step as a same-process ratio against the fastest SUPERCOP baseline:

changeratio
(µcode ÷ fastest)		idea
per-lane D via memory, naive χ with save-MOVs1.00×correct, but a tie
D resident in registers (the RSP 32nd register)0.99×removes ~25 loads/round (§6)
MOV-free χ using the freed D registers0.95×kills ~10 MOVs/round (§8)
θ balanced parity tree + RC byte-index0.93×shortens the round's head and the ι path (§6, §9)

Every one of these exploits the same structural advantage: the cube is fully register-resident, so we have headroom for work that register-starved native assembly cannot do.

12. Measuring honestly: rdtsc, frequency, the real ratio

We compare against all the scalar Keccak variants SUPERCOP ships (x86_64_asm, x86_64_shld, opt64lcu24, opt64lcu24shld) under the same compiler-flag sweep SUPERCOP's autotuner uses, and take the genuinely fastest as the baseline — then time it and the microcode back-to-back in one process.

Why absolute cycle counts can mislead. The timer (rdtsc) counts at a fixed reference rate (~1.1 GHz), not the core's actual clock. When the core bursts to 2.4 GHz the same work reads as ~2.2× fewer ticks. So an absolute "cycles per permutation" is only meaningful when the core is pinned to base frequency. The ratio of two implementations measured in the same process is immune to this — both scale together — which is why we report the ratio as the result.

Concretely: pinned to base frequency, the microcode runs at roughly 1900 cyc/perm and the fastest SUPERCOP variant at ~2045, a ratio of ≈ 0.93. An earlier unpinned measurement reading "874 vs 942" was the very same work timed during a 2.4 GHz burst (the timer undercounting by ~2.18×); the ratio was identical, only the absolute numbers differed. The honest, reproducible statement is the ratio: microcode is ~6–7% faster than the best hand-tuned scalar Keccak on this CPU.

13. The whole round, side by side

The companion guide's §13 states the round as five lines of math. Here is each line and its microcode realization:

companion §13 (the math)our microcode (this guide)
θ: C[x]=⊕yA[x][y]; D[x]=C[x−1]⊕ROT(C[x+1],1); A[x][y]⊕=D[x]balanced XOR tree → C in scratch; D into 5 registers via RSP rotate-temp (§6)
ρ: A[x][y][z] = A[x][y][z − r[x][y]]ROL by RHO[i], fused into the apply pass (§7)

χ: A[x][y]⊕=(¬A[x+1][y])∧A[x+2][y]5 NOTANDs into freed regs, then 5 in-place XORs — MOV-free (§8)
ι: A[0][0]⊕=RC[round]indexed load of RC via byte-counter, XOR into lane 0 (§9)
The mental picture to walk away with. The companion guide's 5×5×64 cube is loaded once into 32 CPU registers (the 25 lanes plus borrowed scratch, including RSP). A single trapped vmwrite then runs all 24 rounds in place — θ smears each lane across its neighbors, ρ twists every word, π reshuffles the words (and conveniently lands them back where they started), χ does the one nonlinear mash, ι stamps in the round constant — looping with a backward branch. Memory is read once and written once. Every speed trick is something native code can't do because it has no spare registers; we do, because the whole cube lives in the register file.
