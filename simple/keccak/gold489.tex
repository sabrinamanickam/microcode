%%%% 6. ABSTRACT %%%%
\begin{abstract}
Cryptographic implementations are traditionally designed for the instruction set architecture exposed by the processor. 
However, modern processors contain deeper execution layers that expose different computational capabilities and constraints. 
In this work, we explore microcode as such an implementation target. 
We present a methodology for implementing cryptographic computation directly in programmable x86 microcode. 
Rather than translating existing native implementations, our methodology treats microcode as a distinct target architecture and maps computation according to its internal state, operation semantics, execution resources, and patch constraints.

We instantiate this methodology on Intel Goldmont with Keccak (f[1600]) and Curve25519 field arithmetic, which exercise different aspects of the microcode domain. 
Our Keccak implementation requires 1896 cycles per permutation, 7.7\% fewer than the fastest native implementation in our comparison. 
For Curve25519, our $(5\times51)$ field multiplication achieves performance comparable to optimized OpenSSL assembly, while our experiments also expose constraints that limit the applicability of microcode. 
These results demonstrate that looking below the ISA exposes a distinct design space for cryptographic implementation and provide a methodology for exploring it.
\end{abstract}

\section{Introduction}

High performance cryptographic software is closely shaped by the execution interface exposed by the processor.
Implementations choose representations, operation sequences, register allocations, and algorithmic variants according to the resources and restrictions of the target architecture.
On x86, this optimization normally ends at the instruction set architecture.
The instructions themselves may be implemented through lower level mechanisms, but these mechanisms are ordinarily hidden from software and are therefore not considered part of the implementation design space.

Microcode provides an opportunity to examine what happens when this boundary changes.
It forms an execution layer below the x86 instruction set and exposes a computational interface that differs from the architectural one.
Prior work on x86 microcode has primarily studied this layer to understand processor behavior, modify existing instructions, or introduce new functionality.
In particular, reverse engineering of Intel Goldmont provides an experimentally accessible microcode environment in which these mechanisms can be studied and modified.
We use this environment for a different purpose.
Rather than treating microcode as an object of reverse engineering, we use it as an experimental platform for studying cryptographic implementation below the ISA.

This perspective leads to a different question from whether cryptographic code can simply be moved into microcode.
We ask how cryptographic implementations change when the execution layer below the ISA itself becomes the implementation target.
The interface exposed at this level differs from the architectural interface for which existing software has been designed.
Understanding these differences therefore requires reconsidering established implementation choices rather than simply reproducing them at a lower level.

We study these effects through a methodology that treats microcode as a distinct implementation target rather than as a lower level encoding of an existing x86 implementation.
The methodology begins by characterizing the microcode execution environment and uses this understanding to systematically explore how cryptographic computation can be mapped to this lower level.
Rather than translating an existing instruction sequence, we design each implementation specifically for the underlying execution layer.
We use the properties of both the computation and the execution environment to derive an implementation suited to the layer on which it will execute. 
This process exposes design choices that are difficult to observe when the ISA is treated as the lowest available abstraction and allows us to identify techniques for exploiting them systematically. 

Cryptography provides a useful setting for this study because optimized implementations already make careful use of the architectural interface.
Competing with these implementations provides a stronger test than demonstrating that computation can execute in microcode.
More importantly, cryptographic code exposes structured dataflow and well understood implementation tradeoffs.
They allow us to examine not only whether an alternative execution interface is competitive but also which properties of that interface change the implementation strategy and under which conditions those changes are useful.

We instantiate this methodology with Keccak $f[1600]$ and Curve25519 as two case studies.
These case studies span symmetric and public key cryptography and present substantially different computational structures, allowing us to study whether common implementation principles emerge when both are designed for the same underlying execution layer. 
More importantly, the two case studies allow us to extract these observations from their individual implementations and formulate them as reusable techniques. 
Our goal is therefore not only to demonstrate cryptographic computation in microcode, but also to understand how knowledge of a lower execution layer can inform the way cryptographic implementations are designed. 

Our work makes the following contributions:

\begin{itemize}[itemsep=1pt, parsep=0pt, topsep=1pt, partopsep=0pt] 
  
  \item We present a methodology for designing cryptographic implementations for programmable microcode. 
  The methodology treats the microcode execution environment as a distinct implementation target and provides a systematic way to reason about the interaction between a cryptographic computation and the underlying processor mechanisms. 
  
  \item We instantiate this methodology for Keccak $f[1600]$ and Curve25519 field arithmetic on Intel Goldmont. 
  Through these case studies, we identify a set of implementation techniques that exploit properties of the microcode execution layer and formulate them so that they can guide implementations beyond the individual constructions studied here. 
  
  \item We evaluate these techniques through controlled experiments that isolate their effect on the resulting implementations. 
  The experiments show how designing with knowledge of the underlying execution layer can change implementation choices made at the architectural level and translate into measurable performance improvements. 
  
  \item We demonstrate the practical potential of this approach with complete implementations on Goldmont. 
  Our Keccak implementation requires 1896 cycles per permutation and outperforms the fastest native implementation in our comparison by 7.7\%. 
  For Curve25519, our microcode field arithmetic is competitive with highly optimized native implementations and provides a second setting in which to study the interaction between the computation and the microcode execution layer.

\section{Background}
\label{sec:background}

We first establish the relevant technical background required to understand this paper. 
This includes the microcode layer of modern x86 processors and the cryptographic primitives we target in our case studies.

\subsection{Intel Microcode}
\label{sec:background-microcode}
Modern x86 processors do not execute all instructions directly.
An internal decode layer translates architectural macro-instructions into sequences of \emph{micro-operations} (\textmu ops)~\cite{koppeReverseEngineeringX862017}.
Frequent or simple instructions are handled by hardwired decoders, whereas complex or infrequent instructions enter the Microcode Sequencer at a fixed entry address, from which the sequencer reads \textmu op sequences from the on-die \emph{Microcode ROM} (MSROM).

During normal execution, the microcode sequencer fetches \textmu ops from addresses in the MSROM. 
A set of \emph{match registers} allows this process to be intercepted. 
Each match register stores an MSROM address.
When the sequencer reaches an address stored in a match register, execution is redirected from the MSROM to a corresponding location in the patch RAM. 
If the address does not match, execution continues normally from the MSROM. 
\Cref{fig:decoder-and-patch} illustrates these two paths.
This mechanism allows selected parts of the existing microcode to be replaced without modifying the MSROM itself. 
Vendors use it to correct processor errata and deploy security mitigations such as those for Spectre and Meltdown~\cite{kocherSpectre2020}. 
We instead use the same mechanism to install cryptographic routines in microcode.
We refer to a self-contained cryptographic routine installed in this way, such as a field multiplication or a complete permutation, as a \emph{kernel}, and to each invocation of a kernel through its triggering instruction as a \emph{firing}.

On the Intel platforms for which the internal microcode format has been studied, microcode is organized as sequences of \emph{triads}~\cite{UCodeDisasm,borrelloCustomProcessingUnitReverseEngineering2023,Libmicro}.
Each triad contains three \textmu ops and one \emph{sequence word}.
The sequence word controls the flow out of the triad and encodes information including the next microcode address, synchronization, and memory barriers~\cite{Libmicro}.
The microcode address space contains a read only region holding the \emph{Microcode Sequencer ROM} (MSROM) together with a writable \emph{patch RAM} in which replacement microcode can reside.
During normal execution, the microcode sequencer fetches from the MSROM, while the patching mechanism can redirect selected microcode entries to the writable region.

Ermolov et al.\ reached the internal microcode state on Goldmont by activating an undocumented debug mode, extracted the microcode, and released disassembly tooling~\cite{UCodeDisasm}.
Later work recovered further details of the microcode organization and the patching mechanism described below~\cite{borrelloCustomProcessingUnitReverseEngineering2023,Libmicro}.

\subsection{Keccak}
\label{sec:background-keccak}

Keccak $f[1600]$ is the 1600 bit permutation used by the SHA 3 and SHAKE functions standardized in FIPS 202~\cite{FIPS202}.
Its state is arranged as a $5\times5$ array of 64 bit lanes $A[x,y]$.
The permutation applies 24 rounds, each consisting of the five transformations $\theta$, $\rho$, $\pi$, $\chi$, and $\iota$, as shown in \Cref{alg:keccak}.

\begin{algorithm}[!ht]
\caption{A round of Keccak $f[1600]$~\cite{FIPS202}. All indices are taken modulo five, $r[x,y]$ and $RC$ are the constants fixed by the specification, and $\mathrm{ROL}$ is a 64 bit left rotation.}
\label{alg:keccak}
\begin{algorithmic}[1]
\Require 1600 bit state $A[x,y]$, round constant $RC$
\Ensure updated state $A[x,y]$
\Statex \textbf{$\theta$ step}
\State $C[x] = A[x,0]\oplus A[x,1]\oplus A[x,2]\oplus A[x,3]\oplus A[x,4]$ \hfill $\forall x$
\State $D[x] = C[x-1]\oplus \mathrm{ROL}(C[x+1],1)$ \hfill $\forall x$
\State $A[x,y] = A[x,y]\oplus D[x]$ \hfill $\forall x,y$
\Statex \textbf{$\rho$ and $\pi$ steps}
\State $B[y,\,2x+3y] = \mathrm{ROL}(A[x,y],\,r[x,y])$ \hfill $\forall x,y$
\Statex \textbf{$\chi$ step}
\State $A[x,y] = B[x,y]\oplus\bigl((\lnot B[x+1,y])\wedge B[x+2,y]\bigr)$ \hfill $\forall x,y$
\Statex \textbf{$\iota$ step}
\State $A[0,0] = A[0,0]\oplus RC$
\end{algorithmic}
\end{algorithm}

\paragraph{Software implementation.}
Efficient software implementations of Keccak use several established techniques to adapt the permutation to the resources of the target architecture, including \emph{plane-by-plane processing}, \emph{in-place processing}, \emph{lane complementing}, and \emph{round unrolling}.

The 25 lanes of Keccak $f[1600]$ occupy 200 bytes before accounting for the intermediate values required during a round.
Scalar x86-64 provides 16 general purpose registers, some of which are also needed for addresses and temporary values.
The complete state and all round intermediates therefore cannot remain simultaneously in architectural registers.
\emph{Plane-by-plane processing} addresses this register pressure by organizing the computation around one five lane plane at a time, which limits the temporary state required during the round~\cite{KeccakImplementation}.

A direct implementation of \Cref{alg:keccak} would also require a separate 25 lane state $B$ for the output of $\rho$ and $\pi$.
\emph{In-place processing} avoids this additional storage~\cite{KeccakImplementation}.
Lane $(0,0)$ is fixed by $\pi$, while the other 24 lane positions form a single cycle~\cite{MakingOfKeccak}.
The lanes can therefore be moved to their new positions using one temporary value.
The rotations of $\rho$ can be applied as the lanes are moved.

The expression used by $\chi$ also requires consideration in scalar software.
Each output lane contains the term $(\lnot b)\land c$.
Implementations that cannot express this term directly can use \emph{lane complementing}, which maintains selected lanes in complemented form and reduces the number of explicit negations required during $\chi$~\cite{KeccakImplementation}.

Finally, the 24 rounds may be partially or fully unrolled~\cite{KeccakImplementation}.
Unrolling removes repeated round control and permits computation across round boundaries to be specialized, at the cost of a larger static implementation.
In particular, a fully unrolled implementation can account for the permutation of lane positions in the register assignment of the following round rather than restoring a common assignment after every round.

\subsection{Curve25519}
\label{sec:background-curve25519}

Curve25519 is the Montgomery curve $y^2 = x^3 + 486662x^2 + x$ over the prime field $\mathbb{F}_p$ with $p = 2^{255}-19$~\cite{PKC:Bernstein06}.
X25519 performs scalar multiplication using only the Montgomery $x$-coordinate.
It evaluates the scalar multiplication with a Montgomery ladder that maintains two projective coordinates $(X_2,Z_2)$ and $(X_3,Z_3)$, processes one scalar bit in each of 255 iterations, and uses conditional swaps to avoid secret-dependent control flow.
\Cref{alg:ladder} gives one ladder step.
Each step performs five field multiplications, four field squarings, and one multiplication by the constant 121665, all in $\mathbb{F}_{2^{255}-19}$.
After the 255 iterations, X25519 converts the result to affine form by computing $X_2 Z_2^{-1}$, which the implementation considered here evaluates with a fixed addition chain of 254 further squarings and 11 multiplications.
Field multiplication and squaring therefore dominate the arithmetic.

\begin{algorithm}[!ht]
\caption{One Montgomery ladder step for X25519~\cite{PKC:Bernstein06}. All operations are in $\mathbb{F}_{2^{255}-19}$, and $X_1$ is the affine input coordinate.}
\label{alg:ladder}
\begin{algorithmic}[1]
\Require $X_1$, $(X_2,Z_2)$, $(X_3,Z_3)$
\Ensure updated $(X_2,Z_2)$, $(X_3,Z_3)$
\State $A = X_2 + Z_2$, \quad $AA = A^2$
\State $B = X_2 - Z_2$, \quad $BB = B^2$
\State $E = AA - BB$
\State $C = X_3 + Z_3$, \quad $D = X_3 - Z_3$
\State $DA = D\cdot A$, \quad $CB = C\cdot B$
\State $X_3 = (DA + CB)^2$
\State $Z_3 = X_1\cdot(DA - CB)^2$
\State $X_2 = AA\cdot BB$
\State $Z_2 = E\cdot(AA + 121665\,E)$
\end{algorithmic}
\end{algorithm}

\paragraph{Field representations and carries.}
Elements of $\mathbb{F}_{2^{255}-19}$ are stored as integer limbs, whose width sets the number of partial products and when carries must propagate.
The portable \texttt{ref10} lineage uses ten limbs of alternating 25 and 26 bits~\cite{PKC:Bernstein06,lib25519}.
Optimized 64-bit implementations commonly use five radix-$2^{51}$ limbs in 64-bit words, as in \texttt{amd64-51}~\cite{bernsteinHighspeed2011}, where the thirteen spare bits per word delay carry propagation between limbs, a multiplication forms 25 limb products, and squaring exploits symmetry for 15 distinct products.
The same five-limb form underlies Fiat-Cryptography with machine-checked proofs~\cite{SP:EPGSC19} and CryptOpt's measurement-driven search~\cite{kuepperCryptOpt2023}, and lib25519 distributes these with portable code such as \texttt{donna\_c64}, selecting per target~\cite{lib25519}.
The alternative saturated $4\times64$ representation of \texttt{amd64-64}~\cite{bernsteinHighspeed2011} needs fewer limb products but leaves no spare bits, so overflow must propagate across word boundaries.
In $5\times51$ the spare bits delay inter-limb carries, but each multiplication still produces low and high halves that \texttt{amd64-51} accumulates with paired \code{ADD} and \code{ADC} across interleaved accumulators before splitting back into radix-$2^{51}$ limbs, folding overflow past bit 255 into the low limb through $2^{255}\equiv19$~\cite{bernsteinHighspeed2011,lib25519}.
The saturated form instead relies on full-width \code{ADC} chains, so the architectural carry flag becomes part of its arithmetic strategy.

\subsection{Terminology}
\label{sec:terminology}

For clarity, we specify the terminology used throughout the paper:

\begin{itemize}[itemsep=2pt, parsep=0pt, topsep=1pt, partopsep=2pt]

\item
\textbf{Macro-instruction.}
An architectural x86 instruction visible to software.

\item
\textbf{Micro-operation (\textmu op).}
An internal microcode operation used to realize architectural computation.
Macroinstructions are implemented as sequences of \textmu ops.

\item
\textbf{Triad.}
A microcode storage unit containing three \textmu ops and an associated sequence word.

\item
\textbf{Patch.}
A sequence of custom microcode placed in writable patch RAM.

\item
\textbf{Hook.}
A redirection from a macro-instruction's microcode entry address to a patch.

\item
\textbf{Firing.}
One execution of a hooked macro-instruction and its corresponding patched microcode program.

\item
\textbf{Kernel.}
A computational region written in micro-operations and placed in patch RAM, independent of the mechanism used to invoke it.

\end{itemize}


\section{Methodology}
\label{sec:methodology}
In this section, we present our methodology for developing cryptographic implementations in microcode.
We first characterize the properties of the microcode domain that affect implementation design.
We then describe the techniques we use to adapt cryptographic computation to these properties.

\subsection{Characterizing the Execution Domain}
\label{sec:characterization}

Before selecting an implementation, we characterize the execution domain according to the properties that affect cryptographic computation.
The purpose of this characterization is not only to identify additional mechanisms, but to determine the implementation choices that these mechanisms permit.

\begin{itemize}[itemsep=1pt, parsep=0pt, topsep=1pt, partopsep=0pt]

\item
\textbf{Available state and its lifetime.}
The execution domain determines the state available to a computation, how condition information is represented, and how long this state remains valid.
These properties govern which values can remain resident during computation and which must be transferred through architectural registers or memory.

\item
\textbf{Operation vocabulary.}
The available operations and their source, destination, and condition semantics determine how a computation can be expressed within the execution domain.
Differences from the architectural instruction set can enable more direct formulations and make transformations required at the ISA level unnecessary.

\item
\textbf{Invocation interface and cost.}
Entering and leaving the execution domain introduces a transition cost together with any transfers required by its architectural interface.
These costs influence the appropriate computation boundary and the amount of useful work and state reuse required within each invocation.

\item
\textbf{Static capacity.}
The available code capacity limits the amount of computation and specialization that can reside in the execution domain at the same time.
This creates a tradeoff between static specialization and dynamic repetition and can constrain which kernels remain resident together.

\item
\textbf{Execution and scheduling resources.}
The issue model, dependency semantics, and available execution resources determine how operations can be scheduled.
These properties govern the independent work that can execute concurrently and the structure of an effective static schedule.

\end{itemize}

Together, these properties define the aspects of the execution domain that govern implementation design. 
The remainder of the methodology uses this characterization to adapt cryptographic computation to the target rather than directly translating an implementation designed for the architectural interface.

\paragraph{Selecting the Computation Boundary.}
\label{sec:method-granularity}

We first decide how much computation to place in microcode.
This decision balances the cost of entering patch RAM against the benefit of executing the computation below the ISA.
The selected region should contain sufficient computation or reusable state to amortize the cost of each invocation. 
At the same time, it should account for a sufficient fraction of the complete computation for improvements within the region to affect end-to-end execution.
We therefore select a computation boundary that contains enough work to justify the transition cost while remaining small enough to fit within the available patch RAM.

We do not require the complete primitive to execute in microcode.
Operations that execute efficiently as native x86 instructions can remain outside the patch, particularly when moving them into microcode provides little benefit.
The native and microcode parts are therefore chosen together rather than treating the patch as a self-contained implementation.

Where beneficial, we extend the patch boundary to keep intermediate state in the temporary registers across consecutive operations.
This avoids returning values to the architectural interface only to load them again for the next part of the computation.
We therefore favour boundaries that allow useful intermediate state to remain live inside the patch.
How far we can extend this boundary is limited by the available Patch RAM capacity.

\paragraph{Representation and Operation Mapping}
\label{sec:method-representation}

We choose the data representation and operation sequence for the microcode domain rather than inheriting them from an optimized x86 implementation.
The representation determines the dataflow available to the patch, while the available micro-operations determine how efficiently that dataflow can be expressed.

We therefore consider representation and operation selection together.
We compare representations by their register pressure, available parallelism, dependency structure, memory traffic, and patch size.
We then map the resulting computation directly to the available micro-operations.

This can lead to choices that differ from optimized native code.
Micro-operation semantics can eliminate instructions required only by the architectural interface, such as copies caused by fixed destinations, or express a computation using fewer operations.
We therefore structure the computation around the properties of the microcode domain rather than directly translating a native implementation.

\paragraph{State Residency and Lifetime.}
\label{sec:method-residency}

We use state available within the execution domain to keep frequently reused values close to their consumers and reduce movement across the execution boundary.'
On Goldmont, we treat the architectural registers and 16 temporary registers as the register space available to the patched program.
This space is allocated according to the dataflow of the complete kernel.
Values that are used frequently or remain live for a large part of the computation receive priority for registers.
When a value is no longer needed, we reuse its register for later computation.
The order of operations and the register allocation are therefore considered together.

Control flow micro-operations also allow us to construct loops entirely within the microcode domain.
A loop body can execute repeatedly while its working state remains in the temporary registers.
This is particularly useful for iterative cryptographic computations, since values reused across iterations do not need to return to the architectural interface.

Not all state needs to remain in registers.
We leave values in memory when their limited use does not justify occupying a register and use the available register space where residency removes more data movement.
Our goal is therefore to allocate registers across the complete firing so that useful state remains resident for as long as it is needed.

\paragraph{Interface Co-design.}
\label{sec:method-interface}

We treat the interface between architectural execution and the microcode domain as part of the implementation design.
Since invoking the hooked instruction transfers control directly to the patch, the interface does not need to follow a conventional function calling convention.
We instead assign fixed architectural registers to the inputs and outputs of each macro-instruction according to the structure of the computation.
This allows the host to place values directly in the registers consumed by the patch without spending operations or patch capacity on argument marshalling.

We choose the output registers with the surrounding computation in mind.
When the result of one firing is consumed by another, we align register assignments where possible so that values can remain in registers across the boundary.
This avoids unnecessary stores and reloads.

The native wrapper is therefore part of the same design.
Its loads, stores, register transfers, and pre-computations contribute to the cost of invoking the macro-instruction.
We optimize the architectural interface and the microcode implementation together to reduce this overhead.

\paragraph{Dependency Restructuring.}
\label{sec:method-restructuring}

We reconsider dependencies that arise from the architectural interface rather than from the computation itself.
Native implementations can contain dependencies caused by fixed destinations, overwritten operands, or shared architectural state.
When these restrictions do not apply in microcode, we restructure the computation to expose independent work.

This can make a sequence with more operations preferable to a shorter but highly serial one.
The goal is therefore not to minimize operation count alone, but to expose independent work that can make effective use of the execution resources available in the microcode domain.

Carry propagation is one example where the microcode domain allows us to remove a dependency imposed by the architectural interface.

\paragraph{Target-aware Scheduling}
\label{sec:method-scheduling}

We schedule the resulting operations according to the dependency semantics, issue model, and execution resources identified during characterization.
On Goldmont, this requires packing the resulting micro-operations into three-slot triads.
Each triad provides three slots, and unused slots cannot be recovered by dynamic scheduling.
We therefore pack operations across the complete computation rather than scheduling individual phases separately.

The sequential semantics of the slots allow some dependent operations to share a triad.
A later slot can consume a result produced by an earlier slot, while a register can be reused after its previous value has been consumed.
We use these properties to reduce the number of triads and make better use of the available slots.

The static size of the schedule also determines how much of the available patch RAM remains for other kernels.
Multiple patches can reside in patch RAM at the same time and can be reached through different hooked instructions.
We therefore consider the combined footprint of all resident patches and use the available capacity where it provides the greatest benefit.

%Operation count, triad count, dependency depth, and patch footprint guide the schedule, but we use hardware measurements to select the final implementation.
We evaluate schedules using both their structural properties such as considering operation count, triad count, dependency depth, patch footprint, and their hardware performance together.

\paragraph{Validation and Refinement.}
\label{sec:method-validation}

We validate each implementation before evaluating its performance.
The generated micro-operation sequence is first checked through simulation and static analysis for register use, condition handling, addressing, control flow, patch capacity, and execution-resource constraints.
After packing, we validate the resulting patch on the target processor against published test vectors or independent reference implementations.
Our transformations preserve secret-independent control flow and memory access patterns.

We distinguish end-to-end performance from the contribution of individual design choices.
Complete implementations establish overall performance, while matched comparisons change one component at a time to isolate its effect.
We use the same approach for ablation experiments that evaluate individual techniques in our methodology.

Measurement also provides feedback to the preceding design decisions.
A representation that appears favourable from operation count may expose an unfavourable dependency structure, a compact schedule may suffer from resource contention, and a kernel that performs well in isolation may lose its advantage once invocation and interface costs are included.
We therefore use empirical results to revisit the computation boundary, representation, state allocation, interface, dependency structure, and schedule where necessary.

\paragraph{Summary of the Methodology}
\label{sec:method-summary}

Our methodology begins by characterizing the execution domain according to its available state, operation vocabulary, invocation interface, static capacity, and execution resources. 
This characterization is then used to select computational boundaries and to co-design the representation, state residency, interface, dependency structure, and schedule of the implementation. 
The native and microcode components are considered together so that crossing the execution boundary forms part of the design rather than a fixed interface around it. 

These decisions are mutually dependent. 
Representation affects state requirements and dependency structure. 
State residency and interface design affect the useful work available within a firing. 
Scheduling determines both dynamic execution and static footprint. 
Static capacity can in turn require changes to the amount of specialization or to the selected computation boundary. 
The methodology is therefore iterative rather than a one-way translation process.

Structural analysis, simulation, hardware validation, and measurement provide feedback throughout this process. 
The resulting implementation is derived from the properties of the execution domain at each stage, from the selection of the computation boundary to the final schedule. 
The case studies in the following sections instantiate this methodology for two substantially different cryptographic computations.

\subsection{Strategy}
\label{sec}

Our strategy is to execute the complete Keccak \(f[1600]\) permutation within a single microcode invocation while keeping its state resident throughout the computation. 
The additional register state available in microcode makes it possible to retain all 25 lanes across the 24 rounds. 
The architectural interface is therefore crossed only when the state enters and leaves the permutation.

To make this possible within the available patch capacity, we use a compact round body that is reused across all rounds rather than unrolling the complete permutation. 
The state representation is chosen so that each round restores the layout required by the next one. 
This allows the same round body to operate repeatedly on the resident state without additional state rearrangement.

Within the round, we adapt established Keccak implementation techniques to the resources exposed by Goldmont microcode. 
In particular, we use in place state transformations where possible and organize intermediate values so that the round can be expressed without materializing a second complete Keccak state.
Together, these choices allow the permutation to remain within microcode while keeping the round representation compact enough to fit within the available patch capacity.

\subsection{Implementation}

In this section, we describe how we realize the strategy above in Goldmont microcode. 
We focus on the allocation and scheduling decisions required to keep the complete state resident, reuse a common round body, and map the Keccak transformations to the resources exposed by the microcode execution layer.

\subsubsection{Whole State Residency and Register Allocation}
\label{sec:residency}

Following the state residency and lifetime principle of \Cref{sec:method-residency}, we allocate the available register space according to how long values remain live and how often they are reused. 
For Keccak, this leads to two main decisions. 
We keep all 25 state lanes resident across the complete permutation, and within each round we reserve the remaining register capacity for the intermediate values with the greatest reuse.

The 25 lanes occupy 13 architectural registers and 12 temporary registers. 
\Cref{tab:regmap} shows this assignment together with the auxiliary registers used during the round. 
The row and column coordinates correspond directly to the Keccak state $A[x,y]$. 
Each lane entry also gives its flat index (i=x+5y) and the rotation offset used by ~$\rho$. 
The notation $\rho k$ means that the lane is rotated left by $k$ bits during the $\rho$ step. 
For example, (A[1,0]) resides in \code{RSI}, has flat index 1, and is rotated by one bit during ~$\rho$. 
The same lane to register assignment holds at every round boundary, which allows the shared round body to operate repeatedly on the resident state.

In addition to the 25 state lanes, \code{RCX} retains the working buffer address while \code{RAX} and \code{TMP12} through \code{TMP15} provide five registers for round intermediates. 
We obtain the remaining temporary register by repurposing \code{RSP}. 
Its architectural value is saved before the permutation and restored before returning to architectural execution.

The choice of which round intermediates occupy these registers is determined by their reuse during $\theta$. 
This transformation first computes the parity of each column and then derives a mixing value that is applied to every lane of that column

\[
C[x] = \bigoplus_{y=0}^{4} A[x,y],
\qquad
D[x] = C[x-1] \oplus \mathrm{ROL}(C[x+1],1).
\]

Keeping both sets together with the complete state would exceed the register budget. 
Each (C[x]) contributes to two (D) values, whereas each (D[x]) is subsequently applied to all five lanes of its column. 
We therefore place the five (C[x]) values in scratch memory and retain the more frequently reused (D[x]) values in \code{RAX} and \code{TMP12} through \code{TMP15}. 
\code{RSP} provides temporary workspace while these values are produced.
This allocation applies the lifetime based policy of \Cref{sec:method-residency} to the dataflow of $\theta$. 
The Keccak transformation itself is unchanged.

\subsubsection{Completing the Round}
\label{sec:cyclewalk}

The remainder of the round is organized around two goals. 
We transform the resident state in place and reuse intermediate registers once their values are no longer needed.
For Keccak, this means combining the application of $\theta$ with the established in place treatment of $\rho$ and $\pi$, then reusing the registers occupied by (D) during $\chi$.

After forming \(D\), we complete \(\theta\) together with the established in place treatment of \(\rho\) and \(\pi\) described in \Cref{sec:background-keccak}. 
The \(\rho\) transformation rotates each lane by a fixed offset, while \(\pi\) moves the rotated lanes to new state positions.

For every lane, the implementation computes

$$
\mathrm{ROL}\left(A[x,y]\oplus D[x],r[x,y]\right)
$$

and writes the result directly to the register corresponding to its destination under \(\pi\). 
The XOR completes the application of \(\theta\), the rotation performs \(\rho\), and the destination register realizes \(\pi\).

As discussed in \Cref{sec:background-keccak}, the 24 lanes other than \(A[0,0]\) form a single cycle under \(\pi\). 
We adopt the established in place traversal of this cycle and use \code{RSP} as the temporary value needed to break it. 
The exact register sequence follows from the Keccak \(\pi\) mapping and the allocation in \Cref{tab:regmap}.

Our implementation specific choice is to realize this traversal entirely between registers while the five \(D[x]\) values remain resident. 
Each lane can therefore receive its \(\theta\) contribution and \(\rho\) rotation as it moves to its \(\pi\) destination. 
This avoids constructing a second 25 lane state and restores the register assignment in \Cref{tab:regmap} when the traversal completes. 
Lane \(A[0,0]\) remains at its original position under \(\pi\) and has rotation offset zero, so only its \(\theta\) contribution must be applied.

The next transformation is \(\chi\), the nonlinear row wise step. For each row it computes

$$
A[x,y]
=
B[x,y]
\oplus
\left(
(\lnot B[x+1,y]) \wedge B[x+2,y]
\right).
$$

At this point the five \(D[x]\) values are no longer live. 
We immediately reuse their registers as the five temporary values required to update one row in place. 
This reuse allows \(\chi\) to execute without allocating another set of registers or copying the row elsewhere.

Goldmont also provides the \uop{NOTAND} operation, which directly computes the nonlinear Boolean term required by \(\chi\). 
We therefore implement each nonlinear term with one \uop{NOTAND} and then XOR the result into the corresponding lane. 
This mapping removes the motivation for using the lane complementing technique discussed in \Cref{sec:background-keccak}. 
The underlying in place treatment of \(\chi\) is established. 
The implementation choice specific to our setting is the reuse of the dead \(D\) registers together with the Boolean operation exposed by Goldmont.

Finally, \(\iota\) XORs a round dependent constant into \(A[0,0]\). 
Since this lane resides in \code{RDI}, the selected round constant is XORed directly into that register. 
The state now again follows the assignment in \Cref{tab:regmap} and can enter the next execution of the shared round body.

\subsubsection{Round Repetition and Patch Interface}
\label{sec:loop}

The complete implementation occupies 108 triads. 
The entry and exit sequences each occupy 26 triads, while the shared round body occupies 56 triads. 
Since a fully unrolled permutation would exceed the 128 triad patch capacity, the round body is reused for all 24 rounds while the Keccak state remains resident in registers.

The 24 round constants are stored consecutively in the working buffer. 
The position within this table also serves as the round state, so no separate round counter is required. 
After each round, the position advances to the next constant and execution returns to the beginning of the shared round body. 
Once the final constant has been consumed, execution proceeds to the exit sequence.

As described in \Cref{sec:background-microcode}, entering a patch requires redirecting the microcode entry of an existing macroinstruction to patch RAM. 
We use \code{VMWRITE} for this purpose. 
Its microcode entry at \code{0x0cd8} is redirected to our patch at \uaddr{7c00}. 
The software wrapper therefore invokes the permutation by executing \code{VMWRITE} with the working buffer base in \code{RCX}.

\subsection{Performance Evaluation}
\label{sec:keccak-eval}

We evaluate the kernel in three steps.
We first compare the complete permutation against every native implementation that runs on this core.
We then measure how much each design choice of \Cref{sec:residency,sec:cyclewalk,sec:loop} contributes to the result.
We finally measure whether the advantage survives inside a complete SHA3-256 computation.

\paragraph{Measurement method.}
We pin execution to one core, disable turbo, and fix the core to its 1100\,MHz base frequency.
Before each sweep we read the \code{APERF} and \code{MPERF} counters under load and confirm a delivered core frequency of 1100\,MHz against a TSC rate of 1094\,MHz, which gives a correction factor of 1.005 between RDTSC ticks and true core cycles.
Every ratio we report remains invariant to this factor.
Each entry reports the median over 200 batches of 1000 consecutive permutations.
\Cref{tab:res-keccak-dispersion} reports the corresponding minimum and the interval between $p_{10}$ and $p_{90}$.
The timed region covers the hooked instruction, the redirection into patch RAM, the 25 input loads, the 24 rounds, and the 25 output stores.
It excludes patch installation, which the wrapper performs once at startup.
All contenders run in the same process and we interleave them batch by batch, so every contender observes the same frequency and the same thermal state.

\paragraph{Constant time behaviour.}
The kernel preserves the input independent control flow and addressing of Keccak $f[1600]$.
The patch contains 108 triads and one conditional operation, which tests the public round constant cursor.
The same cursor addresses the only indexed load.
Every state lane resolves through a fixed displacement, and the patch image fixes every $\rho$ offset.
No data dependent branch and no data dependent address therefore arise during execution.
We assume that the underlying micro-operations have data independent latency, which matches the assumption that constant time native implementations of Keccak already make.

We rebuild each native contender under all 24 compiler and optimisation configurations that SUPERCOP tries and keep its best median, which reproduces the selection that the SUPERCOP autotuner performs.

\section{Case Study 2: Curve25519 in Microcode}
\label{sec:curve25519}
This section presents our implementation of field multiplication and squaring modulo $2^{255}-19$ in Goldmont microcode.
We first examine how existing implementations organize this arithmetic, then describe our strategy and implementation.
We close by evaluating an unsaturated $5\times51$ and a saturated $4\times64$ representation against optimized native code.

\subsection{Challenges}
\label{sec:c25519-challenge}

Existing X25519 implementations on 64-bit x86 primarily use either an unsaturated $5\times51$ or a saturated $4\times64$ representation.
The \texttt{amd64-51} implementation, Fiat Cryptography, and OpenSSL's radix-$2^{51}$ implementation follow the former approach.
The unused bits in each limb allow intermediate values to grow before carries must propagate between field limbs, reducing the frequency of carry propagation during field arithmetic.

This headroom does not eliminate carries within the multiplication itself.
Multiplying two 51-bit limbs produces a result wider than one machine word, and several such products contribute to each output limb.
Implementations therefore accumulate the low and high parts of these partial products across multiple machine words.
For example, \texttt{amd64-51} and OpenSSL's radix-$2^{51}$ multiplication use sequences of \code{ADD} and \code{ADC} to perform these accumulations.
Although the accumulators for different output limbs are largely independent, their carries are communicated through architectural condition flags.
The ordering of the arithmetic must therefore account for the production and consumption of this shared flag state.

Other implementations instead use a saturated $4\times64$ representation.
The \texttt{amd64-64} implementation follows this approach, as do optimized saturated implementations generated by CryptOpt and the radix-$2^{64}$ path in OpenSSL.
Four limbs reduce the number of limb products needed for a field multiplication.
The tradeoff is that each limb occupies a complete machine word, so intermediate overflow cannot be absorbed within unused limb bits.
The arithmetic must instead maintain and propagate carries across full-width words.
Optimized implementations organize their multiplication around these carry chains, with some using multiple architectural flag states where the available instruction set permits it.

Neither representation is uniformly preferable.
The $5\times51$ representation uses more limb products but provides space for intermediate growth, whereas $4\times64$ reduces the product count at the cost of more explicit carry handling.
Existing implementations make this tradeoff within the mechanisms provided by the architectural interface, and their instruction schedules are consequently closely tied to how architectural instructions produce and consume carries.

Microcode exposes a different interface for the same arithmetic.
The challenge is therefore not simply to reproduce one of these established implementations below the ISA, but to determine whether its different mechanisms for representing intermediate condition state favor a different organization of field multiplication and squaring.

\subsection{Strategy}
\label{sec:c-strategy}

We use the unsaturated $5\times51$ representation for our main implementation and place field multiplication and field squaring in separate microcode patches.
These operations expose enough independent arithmetic to use the microcode carry mechanism while remaining small enough to reside together in patch RAM.
The scalar loop, conditional swaps, field additions and subtractions, multiplication by 121665, inversion schedule, and encoding remain in x86 code.

Within multiplication and squaring, we materialize carries into registers rather than propagating each carry immediately through \code{RFLAGS}.
This allows several accumulation chains to progress independently.
Our current multiplication uses five carry accumulators and occupies 58 triads.
A dedicated squaring patch exploits the symmetry of squaring rather than invoking the general multiplication with equal operands.

We reduce the cost of composing these kernels by using fixed register interfaces between x86 and microcode.
The surrounding implementation passes intermediate values directly between consecutive field operations when their register assignments permit it.
This avoids unnecessary stores and reloads without increasing the amount of arithmetic placed in patch RAM.

We also implement the saturated $4\times64$ representation as a control.
Its full width limbs require conventional carry propagation and therefore provide a contrasting mapping to the same microcode interface.
Comparing the two representations lets us determine whether the observed behavior follows from executing arithmetic in microcode alone or from the interaction between the field representation and the mechanisms available below the ISA.

\subsection{Implementation}
\label{sec}

The implementation follows the same principle throughout.
We keep the arithmetic that benefits from the microcode execution model inside the patches and leave the surrounding X25519 computation in x86.
Within the patches, we use the destination associated condition state to separate otherwise dependent carry computations.
Outside the patches, we reduce data movement by matching the register interface of consecutive operations.

\subsubsection{Carry Handling in Microcode}
\label{sec}

An arithmetic $\mu$op records conditional state with its destination.
For an addition, this state includes whether the operation generated a carry.
Our $5\times51$ implementation materializes that carry with \uop{SETCC} and stores the resulting zero or one in a register.
A later addition incorporates the value into the appropriate accumulator.

This organization allows several carry values to remain live independently.
A carry generated while accumulating one partial product does not have to pass through \code{RFLAGS} before another accumulation can proceed.
The patch instead treats the carries as ordinary integer values and combines them when required.

Conventional carry propagation remains available when the representation requires it.
The patch can use \uop{GENARITHFLAGS} to transfer destination associated condition state into \code{RFLAGS}, after which \uop{ADC} consumes the architectural carry flag.
We use this sequence for the saturated $4\times64$ control, where overflow must propagate across complete 64 bit limbs.

The two implementations therefore use different parts of the same microcode interface.
The $5\times51$ implementation separates carry generation from carry accumulation.
The $4\times64$ implementation reconstructs the conventional carry chain required by saturated arithmetic.

\subsubsection{Field Multiplication}
\label{sec}

A $5\times51$ multiplication forms 25 limb products that contribute to five output limbs.
We organize these products so that multiplication, accumulation, and carry handling can progress through separate dependency chains.

Each 64 bit multiplication produces a low half and a high half.
For each output limb, the patch maintains separate accumulators for the low halves, the high halves, and the carries generated while adding low halves.
After an addition to the low accumulator, \uop{SETCC} materializes its carry.
The patch later adds this value to the carry accumulator.
The low accumulator, high accumulator, and carry accumulator can therefore advance independently instead of forming one continuous chain through \code{RFLAGS}.

\Cref{lst} shows the basic schedule.
The first triad adds a low product half, materializes its carry, and prepares an operand for the next multiplication.
The following triad accumulates a high product half, issues the next multiplication, and incorporates the previously materialized carry.
The sequential semantics within a triad established in \Cref{sec} permit this packing.

\begin{lstlisting}[caption={Two triads from the $5\times51$ multiplication schedule. \code{TMP0} accumulates low halves, \code{R8} accumulates high halves, and \code{TMP9} accumulates carries from the low half additions.},label={lst}]
T1 ADD TMP0, TMP0, RDX
SETCC.B TMP15, TMP0
ZEXT RDX, R10
T2 ADD R8, R8, RCX
MUL RCX, R12, RDX
ADD TMP9, TMP9, TMP15
\end{lstlisting}

We repeat this organization for the products contributing to each output limb.
After accumulating the required products, the patch converts the wider accumulators back to radix $2^{51}$.
The unused bits in each limb provide enough space to defer this propagation until the product accumulation is complete.
Overflow beyond bit 255 is then folded into the least significant limb using the reduction relation described in \Cref{sec}.

All partial products and accumulators remain in registers during the patch.
The field multiplication therefore requires no intermediate memory spills.

\subsubsection{Dedicated Squaring}
\label{sec}

We use a separate squaring patch rather than invoking multiplication with equal operands.
As described in the background, symmetry reduces a $5\times51$ square from 25 limb products to 15 distinct products.
The implementation uses this structure directly.

The wrapper prepares the operands required by the squaring schedule before patch entry.
The patch then uses the same separation between low halves, high halves, and explicit carry values as the multiplication kernel.
Radix propagation and the final modular reduction follow the same organization.

The dedicated squaring kernel is small enough to reside together with multiplication in the 128 triads of patch RAM.
This is important because X25519 performs almost as many squarings as multiplications and the final inversion contains long runs of consecutive squarings.
Using the general multiplication kernel for these operations would discard the symmetry available in squaring.

We bind multiplication and squaring to separate repurposed instruction paths.
Both kernels can therefore remain installed while the surrounding X25519 implementation selects the required operation through the hooked instruction.

\subsubsection{Register Chaining Across Field Operations}
\label{sec}

Patch entry is not the only cost at the boundary between x86 and microcode.
A conventional function interface would also reload the input limbs of every multiplication and squaring from memory.
We reduce this movement by matching the output registers of one operation to the input registers required by its consumer.

We implement each Montgomery ladder step in a single inline assembly block and use \code{RBP} to address a fixed layout for the ladder state.
Field addition and subtraction place results directly in the registers expected by the following patched operation whenever the dataflow permits this.

For example, the values corresponding to $A$ and $B$ remain in registers for their subsequent squarings.
The values corresponding to $C$ and $D$ similarly feed the multiplications that form $CB$ and $DA$.
The sums and differences derived from these products remain available for the squarings that follow.
This chaining removes repeated input loads while retaining stores for values that are required by later consumers.

We apply the same idea during inversion.
The fixed addition chain contains several runs of consecutive squarings.
Within a run, the output of one squaring becomes the input of the next without storing and reloading the complete field element.
The wrapper only performs the register rearrangement required by the fixed patch interface.
Memory transfers are required at the boundaries between runs and when values must remain available for later multiplication.

This integration does not change the arithmetic performed by the field kernels.
It reduces the cost of composing those kernels into a complete scalar multiplication.

\subsubsection{Saturated Control}
\label{sec}

We separately implement field arithmetic for the saturated $4\times64$ representation used by \texttt{amd64 64}.
Unlike the main implementation, this representation cannot defer overflow within unused limb bits.
We therefore propagate carries through the architectural carry flag.

After an arithmetic $\mu$op generates destination associated condition state, \uop{GENARITHFLAGS} transfers that state to \code{RFLAGS}.
The following \uop{ADC} consumes the carry.
Repeating this sequence propagates overflow across the four limbs.

The resulting multiplication occupies 75 triads.
This leaves insufficient patch capacity for the specialized squaring algorithm required by the saturated representation while keeping multiplication resident.
The control therefore performs squaring by invoking multiplication with equal operands.

This design deliberately retains the representation used by the native implementation rather than adapting it to favor microcode.
It lets us test whether the benefit observed for $5\times51$ survives when the arithmetic requires conventional full width carry propagation and when patch capacity prevents a dedicated squaring kernel.

\subsubsection{Verification}
\label{sec}

We verify the field kernels before measuring them.
For multiplication and squaring, the test harness compares each microcode result with independent native reference arithmetic.
The tests include boundary values, randomized inputs, and iterated operation chains.

We then validate complete X25519 computations against the RFC 7748 test vectors.
The complete tests exercise scalar clamping, all ladder iterations, inversion, final reduction, and encoding in addition to the patched field operations.
We apply the same validation procedure to the native implementations used in the evaluation.

\subsection{Performance Evaluation}
\label{sec}

We evaluate the implementation with experiments that progressively relax the amount of code held constant.
We first examine individual field kernels and the cost of invoking them.
We then compare field backends inside the same X25519 implementation so that only multiplication and squaring change.
A second controlled experiment replaces the field backend inside the \texttt{amd64 51} framework and separates the effect of the field arithmetic from the effect of ladder integration.
We repeat the controlled replacement for the saturated $4\times64$ representation.
Finally, we compare complete implementations to establish overall performance.

For all complete X25519 measurements, we sweep the compiler and optimization configurations described in \Cref{sec}.
Each contender is measured in the same process with interleaved repetitions.
We report the best median for overall standing and use paired results across the complete configuration sweep when attributing differences between field backends.

Taken together, the experiments show that the Curve25519 result depends on more than the execution speed of individual $\mu$ops.
The $5\times51$ representation exposes independent carry state that maps effectively to the microcode interface.
Register chaining reduces the cost of composing the resulting kernels.
At the same time, repeated patch invocation limits the advantage against a highly optimized backend such as OpenSSL.
The $4\times64$ control establishes a second boundary because full width carry propagation and limited patch capacity remove the structure exploited by the main implementation.

Microcode therefore provides neither a universal improvement nor a universal penalty for multiprecision arithmetic.
Its effectiveness depends on how the arithmetic representation exposes dependencies, how much useful work can be placed behind each patch entry, and whether the required specialized kernels fit within the available patch space.

\subsubsection{Cost of the round}

Table~\ref{tab:roundmix} gives the resulting composition of the round body. The
three techniques of Section~\ref{sec:cyclewalk} are
visible in it. The transport of twenty-five lanes costs fifty micro-ops and no
memory traffic, $\chi$ costs fifty micro-ops and no memory traffic, and of the
eighteen memory accesses that remain, fifteen are the round trip of the column
parities discussed in Section~\ref{sec:residency}.

The table also measures how tightly the round body is packed. Its 152
micro-operations occupy 56 triads, an average of 2.71 of the three available
slots. Packing each step of the table independently would require 59 triads, so
the schedule recovers three triads per round, or 72 over the permutation, by
allowing consecutive steps to share a triad at their boundary. Exactly three
boundaries merge. The last XOR forming $D$ shares a triad with the lane 0 fixed
point of the transport and with the move that breaks the $\pi$ cycle; the final
two XORs of $\chi$ share a triad with the load of the round constant cursor; and
the XOR of the constant into lane 0 shares a triad with the increment and store
of that cursor. The step boundaries are therefore not scheduling barriers, and
loop control in particular costs no triad of its own beyond the one holding the
comparison and the branch.

\subsection{Keccak Microcode Implementation Details}
\label{appkeccakdetails}

This section provides the Goldmont specific details of the Keccak implementation described in \Cref{sec}.
The complete patch contains 108 triads.
It consists of a 26 triad entry sequence, a 56 triad round body, and a 26 triad exit sequence.
The entry sequence saves the architectural stack pointer and loads the 25 Keccak lanes.
The exit sequence stores the 25 lanes and restores the stack pointer.

\paragraph{Invocation and patch entry.}

We install the patch at microcode address \texttt{U7c00} and redirect the microcode entry address \texttt{0x0cd8} to this location.
The architectural wrapper places the working buffer base in \texttt{RCX} and invokes the patch through \texttt{VMWRITE}.
More precisely, \texttt{RCX} points to element 16 of the working buffer rather than its first element.
This choice allows the state, scratch space, loop state, and round constant table to be addressed relative to a single base register.

All patch memory operations use 32 bit addressing.
The wrapper therefore allocates the working buffer below the four gigabyte boundary and checks this condition before invoking the patch.

\paragraph{State register assignment.}

The 25 Keccak lanes remain in registers across all 24 rounds.
Thirteen lanes occupy architectural registers and twelve lanes occupy temporary microcode registers.
The assignment at every round boundary is shown in \Cref{tabkeccakregisters}.
The table follows the state convention $A[x,y]$ used in \Cref{alg:keccak}.

The architectural register \texttt{RSP} is also used as temporary state.
Its architectural value is saved before the state is loaded and restored before returning from microcode.
During the computation of $D[x]$, \texttt{RSP} holds loaded and rotated column parity values.
It is then reused as the single temporary value that closes the 24 lane in place traversal.

\paragraph{Working buffer layout.}

The working buffer contains 56 64 bit words.
The first 25 words contain the input and output state.
Five additional words hold the column parities $C[x]$.
The remaining words contain the round control state, the saved stack pointer, and the 24 round constants.

\begin{table}[!ht]
\centering

\begin{tabular}{@{}llr@{}}

The state is stored in row major order with buffer position $x+5y$ corresponding to $A[x,y]$.
Since \texttt{RCX} points to buffer word 16, the first state lane is addressed at displacement $-128$ and the final state lane at displacement $64$.

\paragraph{Computation of $\theta$.}

The five column parities are computed sequentially using \texttt{RAX} as the accumulator and are stored in buffer words 25 through 29.
The stored values are then used to form the five $D[x]$ values

$$
D[x] = C[x-1] \oplus \mathrm{ROL}(C[x+1],1).
$$

The implementation assigns

$$
D[0]\rightarrow\texttt{RAX},
\qquad
D[1]\rightarrow\texttt{TMP12},
\qquad
D[2]\rightarrow\texttt{TMP13},
\qquad
D[3]\rightarrow\texttt{TMP14},
\qquad
D[4]\rightarrow\texttt{TMP15}.
$$

The intermediate rotations of the stored column parities use \texttt{RSP} as scratch state.
Once the five $D[x]$ values have been formed, no further access to the stored $C[x]$ values is required during that round.

\paragraph{In place traversal.}

Lane $A[0,0]$ remains in \texttt{RDI}.
Its $\theta$ contribution is applied directly and no rotation is required.
The remaining 24 lanes are processed using the single cycle induced by $\pi$.
The patch realizes this cycle through the following sequence of register replacements

$$
\begin{aligned}
\texttt{R9} &\leftarrow \texttt{R12}
\leftarrow \texttt{TMP9}
\leftarrow \texttt{TMP1}
\leftarrow \texttt{TMP7}
\leftarrow \texttt{RBX}
\leftarrow \texttt{R15}
\leftarrow \texttt{TMP0} \\
&\leftarrow \texttt{TMP6}
\leftarrow \texttt{TMP10}
\leftarrow \texttt{TMP2}
\leftarrow \texttt{RBP}
\leftarrow \texttt{TMP11}
\leftarrow \texttt{TMP8}
\leftarrow \texttt{R11}
\leftarrow \texttt{TMP3} \\
&\leftarrow \texttt{R8}
\leftarrow \texttt{RDX}
\leftarrow \texttt{TMP5}
\leftarrow \texttt{TMP4}
\leftarrow \texttt{R14}
\leftarrow \texttt{R10}
\leftarrow \texttt{R13}
\leftarrow \texttt{RSI}.
\end{aligned}
$$

The original value of \texttt{R9} is saved in \texttt{RSP} before the first replacement and is written into \texttt{RSI} to close the cycle.
Each replacement also applies the appropriate $D[x]$ value and the fixed $\rho$ rotation before writing the destination.
Consequently, the traversal simultaneously realizes the lane update from $\theta$, the rotations from $\rho$, and the permutation from $\pi$.
After the final replacement, the register assignment again matches \Cref{tabkeccakregisters}.

\paragraph{Implementation of $\chi$.}

The five registers that previously contained $D[x]$ are reused for the nonlinear terms of one row.
For each row, the patch first evaluates all five expressions

$$
T[x] = (\lnot A[x+1,y]) \land A[x+2,y]
$$

using \uop{NOTAND}.
Only after all five values have been formed are they XORed into their corresponding state lanes.
This ordering preserves the original row values until every nonlinear term depending on them has been computed.
The same five temporary registers are then reused for the next row.

\paragraph{Round constants and loop control.}

Buffer word 30 contains a byte offset into the round constant table.
Before the first round, this offset is initialized to 128, which selects \texttt{RC[0]} relative to the \texttt{RCX} base.
After $\chi$, the patch loads the current offset, uses it to load the corresponding round constant, and XORs the constant into \texttt{RDI}, which contains $A[0,0]$.

The offset is then increased by eight bytes and written back to buffer word 30.
The updated value is compared with 320.
If it differs, a conditional microcode jump returns to the start of the shared round body at \texttt{U7c68}.
The successive offsets are therefore 128 through 312.
After the final round the updated value becomes 320 and execution continues to the exit sequence.

\paragraph{Patch layout.}

The patch starts at \texttt{U7c00}.
The first 26 triads save \texttt{RSP} and load the 25 state lanes.
The shared round body begins at \texttt{U7c68} and occupies 56 triads.
The final 26 triads store the 25 state lanes and restore \texttt{RSP}.
The resulting layout is shown in \Cref{tabkeccakpatch}.

\begin{table}[!ht]
\centering
\caption{Static layout of the Keccak patch.}
\label{tabkeccakpatch}
\begin{tabular}{@{}lr@{}}
\toprule

\midrule

This leaves 20 of the 128 available patch triads unused.
The repeated round body therefore allows all 24 rounds to execute within one invocation while retaining sufficient space for the state transfer code.
